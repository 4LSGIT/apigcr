# DBKQ → YisraForm: the on-submit workflow, click by click

**Slice:** D3. **Written:** 2026-09-04. **Executed by:** Fred, through the
workflow builder UI. **Verified by:** manager, via readonly SQL.

**No SQL.** Workflows are versioned (`workflow_steps.version`, published via
`workflows.current_version`), so a hand-inserted step row is invisible to the
engine until a publish bumps the version — and a hand-inserted row at the wrong
version is worse than no row. wf48 is the precedent for how painful that is.
Build it in the UI.

---

## 1. What this workflow is FOR

wf48 ("Jotform - Detailed BK Questionaire", v3, 23 steps) is the incumbent
side-effect checklist for a DBKQ submission. Under YisraForm most of it is
already handled by the platform:

| wf48 did | YisraForm equivalent |
|---|---|
| steps 1–4: pull the submission from the JotForm API, flatten answers | the submission IS the payload — `_values` rides in the dispatch |
| steps 6–15: resolve the case folder, render+save the PDF, wait, re-list, recover the path, share-link it | `onSubmit.pdf: true` → wf40 step 3 self-calls `POST /api/forms/submissions/:id/pdf/file` → `formPdfService.fileSubmissionPdf` → `filePlacementService.placeAndRegister` (subfolder `Forms`) |
| step 16 + 23: build and send the office email | wf40 steps 1 + 4 |
| step 20: write the case log row | wf40 step 8 |
| step 17: "case-linked work?" gate | wf40 step 5 (`Linked?`) for its own branch; this workflow re-gates for its own |
| **step 19: cancel the `dbkq_reminder` drip** | **nothing — this workflow** |
| **step 22: stamp `cases.case_detailed_form`** | **nothing — this workflow** |

So the delta is exactly two side effects, plus the case gate and the contact
lookup they need. **Five steps.**

Hook 39 + wf48 stay live and untouched for the JotForm tail. This workflow can
only ever fire from a YisraForm `dbkq` submission.

## 2. Facts this rests on (manager-verified 2026-09-04)

**The dispatch's system fields** (`routes/api.ext.forms.js:340–371`) — assigned
last, so they beat any submitted field or entry initData of the same name:

```
form_key       'dbkq'
form_title     'Detailed Bankruptcy Questionnaire'
link_type      'case'  |  ''      ← '' when the submission degraded to unlinked
link_id        <case_id> | ''
submission_id  <form_submissions.id>          ← THE ANSWER TO THE D3 DISCOVERY ITEM
make_pdf       true                            (from onSubmit.pdf)
_values        { …every submitted field… }
```

`submission_id` is present and templatable as `{{submission_id}}`. No blocker.

**The execution's contact is bound but NOT readable.** `api.ext.forms.js:392`
passes `contact_id_override` from the server-resolved Primary, which populates
`workflow_executions.contact_id`. That column is **not** exposed as a
placeholder — `workflow_engine.resolveSingle` reads only `variables`, `this.*`
and `env.*`. And `cancel_sequences` hard-requires an explicit `contact_id`
(`lib/internal_functions/sequences.js:36`). **Therefore step 3 below must look
the Primary up itself**, exactly as wf48 step 18 did. This is not redundant
with the override; there is no way to read the override back.

**`cases.case_detailed_form`** is `varchar(20)`. `yf:` + a submission id fits
for ids up to 17 digits; current max is 5 digits. Fine.

## 3. The workflow

**Name:** `YisraForm - Detailed BK Questionnaire`
**Active:** yes (leave it active — it cannot fire until the `onSubmit` block in
§4 is published, and §4 is a later runbook step).
**default_contact_id_from:** leave NULL. The external route passes
`contact_id_override`, which outranks it, and a non-NULL value here would let a
submitted field named the same thing choose the execution's contact on any
OTHER dispatch path.

### Step 1 — `Case-linked?`  (internal_function)

```json
{
  "function_name": "evaluate_condition",
  "params": {
    "variable": "link_type",
    "operator": "==",
    "value": "case",
    "then": 2,
    "else": null
  }
}
```

error_policy: `abort`.

**Why `link_type` and not `link_id`:** the external route sets both together
(`linkType='case'` / `linkId=caseId`, or `('','')`), and `link_type` is the one
wf40 step 5 already gates on — same signal, same spelling, one convention.

**`else: null` ends the workflow.** An unlinked (degrade-mode) submission does
NOT get its case steps: there is no case to cancel a drip on and no case to
stamp. **wf40 still runs independently and still notifies** — its step 5/6 path
sends the RG unlinked alert — so a degraded submission is visible in the Form
Inbox and staff re-link it with `PATCH /api/forms/submissions/:id/link`.
Re-linking after the fact does **not** retro-fire this workflow; the reminder
drip keeps running and `case_detailed_form` stays blank until someone stamps it
by hand. That is a known, accepted gap for a path that should be rare (the link
is generated by our own sending form) — say so out loud rather than building a
retro-fire.

### Step 2 — `Primary contact`  (internal_function)

Replicates wf48 step 18 verbatim except for the case-id variable.

```json
{
  "function_name": "query_db",
  "params": {
    "from": "case_relate",
    "select": ["case_relate.case_relate_client_id"],
    "where": [
      { "column": "case_relate.case_relate_case_id", "op": "=", "value": "{{link_id}}" },
      { "column": "case_relate.case_relate_type",    "op": "=", "value": "Primary" }
    ],
    "order_by": [{ "column": "case_relate.case_relate_client_id", "dir": "asc" }],
    "limit": 1,
    "format": "first"
  },
  "set_vars": { "primary_contact_id": "{{this.output.case_relate_client_id}}" }
}
```

error_policy: `retry_then_abort`, max_retries 1, backoff 5s.

**The `ORDER BY … ASC` + `limit 1` is load-bearing, not decoration.** Two
contacts can both be Primary on a case (wf48's own step note cites
`caseService.searchCases:679`); the MIN-by-id rule is how every other reader of
this table picks one, and picking differently here would cancel a drip enrolled
against the other contact — i.e. not cancel it at all.

### Step 3 — `Cancel reminder`  (internal_function)

```json
{
  "function_name": "cancel_sequences",
  "params": {
    "contact_id": "{{primary_contact_id}}",
    "template_type": "dbkq_reminder",
    "reason": "dbkq_submitted"
  }
}
```

error_policy: **`ignore`**, max_retries 0.

Same config, same `reason` string, same error policy as wf48 step 19. Keep
`ignore`: wf48's step note records that 0 of 1081 cases lacked a Primary, but a
blank `contact_id` throwing here would abort before step 4 and leave the case
un-stamped — a worse failure than a drip that keeps running. Cancelling **by
type** is why `DBKQ_SEQ_TYPE` in `sendingform-bk.html` and this string have to
stay in agreement; `tests/sendingformBk.dbkqLink.test.js` locks the other end.

### Step 4 — `Stamp case_detailed_form`  (internal_function)

```json
{
  "function_name": "update_case",
  "params": {
    "case_id": "{{link_id}}",
    "fields": { "case_detailed_form": "yf:{{submission_id}}" }
  }
}
```

error_policy: `retry_then_abort`, max_retries 1, backoff 5s.

**Three deliberate divergences from wf48 step 22:**

1. **`case_detailed_link` is NOT written.** wf48 wrote the Dropbox share link
   there and `case.html` read it to iframe the PDF. Under YisraForm the tab
   renders the live submission instead (`detTabSrc`, D3.1a), so a link column
   here would be a second source of truth for the same fact — and the one that
   loses. The 126 legacy rows keep theirs; new rows get none.
2. **No `Update case?` gate.** wf48 step 21 gated on `detailed_link` being
   non-empty, because a failed Dropbox filing meant there was nothing to point
   at. Here the fact being stamped is the submission id, which exists
   unconditionally by the time this step runs. A PDF failure must NOT suppress
   the stamp — the client did submit.
3. **The `yf:` prefix.** This is what makes the column self-describing:
   bare-numeric = legacy JotForm, `yf:` = YisraForm. `case.html`'s `detTabSrc`
   branches on exactly this, and template 29's reminder condition
   (`case_detailed_form IS NULL`, `sequenceEngine.js:153` treating `''` as null)
   is indifferent to the shape — it only cares empty vs not.

**Ordering matters.** Cancel (step 3) runs BEFORE the stamp (step 4) on
purpose: the stamp is what makes a future re-enrolment's condition fail, so
stamping first and then failing to cancel would leave a running drip that can
never be re-cancelled by re-running this. The cheap side effect goes first.

### Step 5 — none

Step 4 is the last step. Nothing follows.

## 4. The `onSubmit` block for the `dbkq` definition

Paste into the `dbkq` template's definition in the builder, then **republish**.
`<NEW_ID>` is the id the builder assigns the workflow in §3.

```json
{
  "pdf": true,
  "workflows": [
    {
      "id": 40,
      "initData": {
        "form_label": "Detailed BK Questionnaire",
        "log_subject": "Detailed Bankruptcy Questionnaire received",
        "title_field": "q1_name_last_name",
        "notify_to": "shoshana@metrodetroitbankruptcylaw.com",
        "labels": [
          ["First name",            "q1_name_first_name"],
          ["Last name",             "q1_name_last_name"],
          ["Marital status",        "q103_maritalstatus"],
          ["Spouse",                "q245_whatIs245"],
          ["Dependents",            "q39_dependnum"],
          ["Household size",        "q108_houshold"],
          ["Housing",               "q98_housing"],
          ["Owes a mortgage",       "q70_Qowemortgage"],
          ["Owns vehicle(s)",       "q72_CarOwn"],
          ["Currently working",     "q32_areYou32"],
          ["Employer",              "q140_WorkWhere"],
          ["Spouse working",        "q37_isYour"],
          ["Owned a business (4y)", "q114_Qamybusiness"],
          ["Military service",      "q266_wereYou"],
          ["Emergency contact",     "q208_emergencyContact208_first_name"],
          ["Emergency phone",       "q208_emergencyContact208_phone_number"]
        ]
      }
    },
    {
      "id": "<NEW_ID>",
      "initData": {}
    }
  ]
}
```

### Why these labels, and why only these

wf40 step 1's formatter (`Format answers + subject (generic)`, v2) falls back to
prettified keys for **every** value when `labels` is absent. On a 252-field form
that is a 252-row email — and worse, because the DBKQ's field names are
JotForm-derived (`q283_approximatelyHow283_personal_care_products`), the
prettifier produces "Q283 Approximatelyhow283 Personal Care Products". So
`labels` is not optional here, it is load-bearing.

The formatter **drops empty values**, so a curated list of 16 self-shrinks to
whatever the client actually answered. The 16 are the ones that tell SB, in one
screen, what kind of case just landed: who, family shape, housing, vehicles,
income, and the two flags that change the work (a business in the last four
years, military service). **Everything else is in the attached PDF**, which is
the point of `pdf: true` — the email is a triage notice, not a data dump.

Two named-out omissions:

- **No expense fields.** ~60 of the 252 are monthly-expense line items. They
  matter enormously to the petition and not at all to "should I look at this
  today", and they would swamp the list.
- **No `q1_name_*` composite.** wf40's `title_field` is a **single** key
  lookup (`values[title_field || 'name']`), so the subject can carry first OR
  last, not both. `q1_name_last_name` is chosen because the firm files by
  surname; the full name is the first two rows of the body.
  **This is a real regression from wf48**, whose step 4 built
  `first + ' ' + last` and put the full name in the subject. Fixing it properly
  means adding a composite to wf40's formatter, which is a shared workflow and
  out of D3's scope. Flagged, not worked around.

`notify_to` is **read from wf48**, not assumed: step 16's custom_code sets
`to = SB` where `SB = 'shoshana@metrodetroitbankruptcylaw.com'` on both
successful branches, and `IT = 'it@4lsg.com'` only on the could-not-file
failure branch. wf40 has no failure branch of that kind (its PDF step is
`error_policy: ignore` and the email sends regardless), so SB is the whole
answer.

`form_label` is set explicitly rather than letting the formatter clip
`form_title` at 45 chars — "Detailed Bankruptcy Questionnaire" is 32 and would
survive, but the email subject reads better short, and `log_subject` then
matches wf48 step 20's subject string exactly so the case log looks continuous
across the cutover.

The second entry's `initData` is `{}` on purpose: every variable that workflow
needs (`link_type`, `link_id`, `submission_id`) is a system field the dispatcher
always injects.

### One difference staff will notice

wf48 sent from `automations@4lsg.com`. wf40 step 4 sends from
`stuart@4lsg.com`. Not changed here — wf40 is shared with the intake form and
its From address is not D3's to touch. Worth a heads-up to SB so the new mail
isn't filtered.
