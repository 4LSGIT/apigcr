## 0. Decisions (2026-10-08)

- **D1 — Storage:** metadata + text bodies inline in MySQL; attachments NOT copied at ingest — structure only, fetched on demand from IMAP; GCS archival (raw .eml + attachments) is a later slice behind reserved pointer columns. Nothing gates on the Cloud SQL move.
- **D2 — Coupling:** core is built to the protocols — IMAP (ingest/read) + SMTP via existing adapters (send) — which de facto covers any standards host. Provider-specific code is confined to an optional **provisioning driver** (Migadu first). Credential *acquisition* is the driver's job; credential *use* is always generic IMAP/SMTP — the transport never knows which provider it's talking to. API-transport providers (Gmail API, MS Graph) are out of scope for the core; if YC3 ever needs tenant-BYO Gmail/M365, evaluate embedding EmailEngine rather than hand-building.
- **D3 — Credential model:** preferred: per-mailbox **Migadu identities** — YC gets its own login per mailbox, independent of the human's password (rotation-safe, individually revocable). Pending trial test T1. Fallback if identities can't do IMAP login: YC-issued mailbox passwords (Fred mints them, so rotation stays controlled). Either way `mailboxes` stores plain host/user/secret and the transport is unaffected.
- **D4 — Worker placement / ingest mode:** prod is Cloud Run (`svpcac`) — no box, no systemd. v1 ingest is **poll-based**: Cloud Scheduler (or Cloud Tasks) hits an authenticated job endpoint every 5 min (config knob), lock-guarded and bounded per run (§4.1). Latency parity with today: the Apps Script source lands on a ~5-min cadence in `email_ingest_executions`. IMAP IDLE is deferred — revisit only if the VM per `ref/plans.md` lands or a real latency requirement appears; then a dedicated Cloud Run service (min=max=1, CPU always allocated), which still needs reconnect logic + the lock (rolling deploys overlap instances).
- **D5 — Sequencing:** the mailbox system is built BEFORE the Migadu migration executes (provider-plan S1+). The DB→Cloud SQL move is funding-gated and does not compete for this slot. Only the trial-account tests run beforehand (T1 below; T2 + MS first-contact per the provider plan) — they gate the migration stages, not this build. The cutover then lands on a working system, and a later provider swap per mailbox is just repointing its `mailboxes` row (host/user/secret) with the §4.1 UIDVALIDITY re-key absorbing the new UID world.
- **D6 — Channel-general access, email-only NEW store:** the access model and UI shell generalize across channels; storage does not. Grants are `channel_grants` (§3) — 'mailbox' now, 'phone_line' later against the existing `phone_lines` rows — and the v1 UI ships as a comms hub (§4.4) with Email live and Phone as a later slice. **Amended 2026-10-11 (ruling; it corrects a factual error):** the phone tab reads `phone_event_log` — the YC phone store that already exists, written on every phone event by the ingest pipeline (AI_CONTEXT §28: both providers, suppressed events included, bodies; 10,441 events since 2026-05-31, RingCentral 2 of the 5 active lines and 77% of the events) — scoped by `channel_grants('phone_line')`. The Quo adapter stays for SEND and for fetching recordings. The original "reads Quo LIVE, no YC phone store" would have missed most of the traffic (Quo carries none of RingCentral's). No NEW phone store is built in this arc; the recordings arc owns recordings/transcripts, on the same two-tier + grants patterns. Grant checks sit on INTERACTIVE routes only — never inside emailService/phoneService — so workflow/automation sends are untouched.

## 1. Goal

Every user gets personal inbox(es); some users hold several addresses (billing@4lsg + shoshana@mdbl); users can be granted read and/or send access to others' mailboxes; SU and SS see everything; each user composes a "mixed inbox" from the mailboxes they can read, with custom saved views. YisraCase is the access-control and UI layer; the provider supplies storage and transport.

**Two-tier record (the organizing principle).** Tier 1 — the mailbox store (`mail_messages`): complete — every message in every ingested folder — and access-controlled by grants. Tier 2 — the log: curated and firm-visible; the rules/suppression/firm-to-firm pipeline is the valve between the tiers, and `log_id` is the bridge. The principle extends per channel: `phone_event_log` is phone's tier-1 store (complete, both providers — D6 as amended), the phone log rows its tier 2; the recordings arc adds recordings and transcripts later.

## 2. Architecture boundary (per D2)

```
                      ┌────────────────────────────┐
  Migadu admin API ──▶│ provisioning driver (opt.) │  mints mailboxes/identities,
  (or manual panel)   └──────────┬─────────────────┘  writes credentials rows
                                 ▼
                     mailboxes table (host/user/secret — provider-blind)
                                 ▼
          ┌──────────────────────┴──────────────────────┐
          ▼                                             ▼
  imapTransport.js (ONE module owns all IMAP)    emailService + adapters (send, exists)
          ▼                                             ▼
  ingest worker → canonical envelope → emailIngestService (rules/suppression/case-link, exists)
                → mail_messages
```

- All IMAP calls live in `services/mailbox/imapTransport.js` — not an interface framework, just discipline. A future JMAP module would be a sibling, added only when real.
- Hostnames/ports are config/row data, never constants.
- Not just a pilot path: from S1 the worker **is the ingest for the current providers** — SiteGround mailboxes over `gcam1191.siteground.biz:993` and the Workspace account over Gmail IMAP — pre-migration, superseding the dead exim/PHP relay (ingest source 2, dead since 2026-05-27; provider-plan S1 keeps its deactivate+delete cleanup). The Apps Script source retires parity-gated: ~14 clean days of Gmail-IMAP ingest feeding the same pipeline, no later than provider-plan S3. **Dedupe does NOT cover the overlap by itself** — `email_log` dedupes on `(source, message_id)` per source only (AI_CONTEXT §27), and `gmail-firm` keys on Gmail's internal id while the worker's default is the RFC Message-ID under `mailbox-imap`. The overlap is safe only because the Gmail mailbox emits under `gmail-firm` keyed by hex(X-GM-MSGID) — the Apps Script key — via the S1-G emission override (§4.1), verified live before it emits (`ref/MAILBOX_GMAIL_PARITY.md`). The same per-source rule keeps **SiteGround boxes that forward into the Workspace inbox store-only**: their `mailbox-imap` copy would cross-source-duplicate the Gmail copy until those forwarders die at the Migadu migration.
- No process-global state: `mailboxService`/`imapTransport` hold no module-scope caches of mailbox/grant data and no persistent IMAP connections — per-run connections (ingest) and per-request connections (part fetch) only (tenancy audit §A3 / P0-5).

## 4. Components

### 4.1 Ingest worker
Poll-based per D4 (suggest `imapflow`). Each run: `GET_LOCK(CONCAT('mailbox_ingest:', DATABASE()), 0)` — skip if held (`fieldDefReconciler` pattern; the name is DB-suffixed from day one because the lock namespace is server-global — possibly-shared SG MySQL today, YC3 P0-6 tomorrow); iterate `ingest_enabled` mailboxes; connect, fetch UIDs newer than the `ingest_state` cursor, process, advance cursor, disconnect. Bounded runtime — stop and leave the remainder for the next tick rather than overrun. Dedupe by `(mailbox, folder, uid)`, secondarily `message_id`; the trigger is at-least-once, so a re-run must be a no-op. Backoff on errors; capped concurrency.

**UIDVALIDITY change ⇒ re-key, never blanket-purge.** Purging the folder's rows would cascade into `mail_read_state` and orphan `log_id` bridges — users' read markers and case links on old mail would vanish. Instead: re-scan the folder, re-map stored rows to their new UIDs by `message_id`, insert unmatched messages, purge only true orphans (stored rows with no match). Rows whose `message_id` is missing or ambiguous within the folder don't re-map — they fall through to insert + orphan-purge. The rules pipeline is safe either way (`emailIngestService` reports re-emitted envelopes as `duplicate`). Mechanics: re-mapping collides with `UNIQUE(mailbox_id, folder, uid)` mid-update — a row's new UID can equal another row's old UID — so re-key in two phases: park affected rows' `uid` to NULL (nullable for exactly this), then set finals.

Per D1, the worker fetches envelope + text parts + BODYSTRUCTURE only — attachments are not downloaded. On-demand endpoint (`GET /api/mailboxes/:id/messages/:mid/parts/:part`) streams the part from IMAP when a user opens it, grant-checked — a request-scoped connection, unaffected by D4. Caveat accepted for v1: if a message is deleted server-side (webmail/Outlook), its attachments are gone from YC too; the GCS archival slice removes this. Exception hook: ingest rules that *need* a binary (court pipeline PDFs) may materialize those parts at ingest into the existing case-file path — rule-driven, not default.

**Pipeline reuse (key decision):** the worker emits the existing canonical envelope into `emailIngestService` — same path as the Apps Script / `POST /api/email/ingest` sources, registered as a new row in `email_ingest_sources`. Rules, suppressions, firm-to-firm skip, executions logging, and case-linking work unchanged. Additionally it writes the full message into `mail_messages` (`log_id` bridges). Apps Script source retires parity-gated (§2), no later than provider-plan S3.

**Emission identity (S1-G).** Which `(source, message_id)` a mailbox's mail is emitted under IS its dedupe space. Default: `mailbox-imap` + RFC Message-ID. Override (`mailboxes.emit_source_name` + `emit_id_kind`, SU PATCH only, set as a pair, active source row required, `provider` never under `mailbox-imap`, one provider-keyed mailbox per source): emit under another source keyed by the RFC id or by `mail_messages.provider_id`. The transport captures Gmail's X-GM-MSGID (imapflow surfaces it as `emailId` on X-GM-EXT-1 servers that do not advertise OBJECTID) as lowercase hex — the id Gmail's web UI, API and Apps Script use. A provider-keyed message without a provider id is stored, counted and alerted, **never** emitted under the RFC id (that would mint a second identity). Where present, the provider id is also the secondary-dedupe and re-key identity. The override never changes which folders emit or whether history emits. Runbook + live gate: `ref/MAILBOX_GMAIL_PARITY.md`.

**Backlog policy (S1-G).** `ingest_folders.<folder>.backfill:false` stores only mail arriving after first sight (decided then; a later UIDVALIDITY re-key backfills only above the highest re-mapped UID). For large accounts — the Workspace INBOX holds 62k messages; a full backfill would exceed Gmail's ~2.5 GB/day IMAP download cap and multiply the SiteGround DB. Bounded history (the 2-year cutoff) stays S4's.

**Per-folder rules policy (v1):** the worker consults `mailboxes.ingest_folders` — only folders flagged `emit_to_rules` (default: INBOX yes, Sent no) emit into the rules pipeline; everything ingested is stored to `mail_messages` regardless. Deliberate consequences: externally-sent mail (Outlook/Apple Mail) becomes visible in the mailbox tier immediately but reaches the log tier only if a later rule opts Sent in; YC's own APPENDed sends are stored without re-entering the pipeline.

**Amendment — provider-id mailboxes emit sent mail (ruling 2026-10-11).** A mailbox emitting under a provider-keyed override (the Workspace box as `gmail-firm`) emits its OUTBOUND mail too: the Apps Script source already posts every sent message (51 of 51 sampled 2026-10-09, sent-only threads included), so this is parity, not new exposure — firm-to-firm skip, suppressions and direction-by-firm-domain apply exactly as they do to the Apps Script copy, and the two copies collide on one `email_log` row. Firm replies keep reaching the log after the Apps Script retires. For that mailbox "YC's own APPENDed sends are stored without re-entering the pipeline" no longer holds: anything sent through the account (today: YC automation mail sent as `automations@4lsg.com` through it, which the Apps Script also posts) re-enters the pipeline as the Apps Script copy does — S3's Sent APPEND must design for it. RFC-keyed mailboxes (SiteGround, `mailbox-imap`) are unchanged: Sent stays opt-in, store-only by default.

**Gmail: All Mail as the ONLY folder (ruling 2026-10-11).** Gmail exposes each label as an IMAP folder; a message keeps one X-GM-MSGID across every folder it appears in, with a different UID in each. The sanctioned Gmail configuration polls `[Gmail]/All Mail` alone — one copy of inbound, sent and label-filed mail (filters file ~43% of the Workspace box's mail outside INBOX, with automations riding some of those labels), so a new filter can never open a coverage gap. All Mail ALONGSIDE any other folder stores every labelled message twice (secondary dedupe is per folder; emission would still dedupe at `email_log`) — never do that; the SU folder listing warns `ALL_MAIL_ALONGSIDE_OTHER_FOLDERS` (special-use `\All` from the server, so localized names are caught). Spam and Trash are outside All Mail.

**Gmail labels (S2-L, OQ5).** On a server advertising X-GM-EXT-1 the transport asks X-GM-LABELS in the SAME fetch (imapflow `labels`; no extra round trip) and the worker stores them as fetched in `mail_messages.gmail_labels` — system labels keep their backslash (`\Inbox`, `\Sent`, `\Important` …), user labels as named, `[]` = none (archived); NULL on every other host and on rows stored before S2-L. A SNAPSHOT: archiving or relabelling in Gmail after ingest is not seen. One label decides something: `\Draft` marks a draft (next paragraph). Beyond that, labels change nothing the worker decides — stored / emitted / keyed exactly as before; the envelope does not carry them. The SU route `POST /api/mailboxes/:id/labels/snapshot` re-fetches them for stored rows of a POLLED folder (the backfill for pre-S2-L rows and the only refresh until S4): UID FETCH of UID + X-GM-LABELS, bounded (`limit` ≤ 1000, loop on `next_after_uid`), under the ingest lock (`GET_LOCK(CONCAT('mailbox_ingest:', DATABASE()), 0)`, skip if held), only when the server's UIDVALIDITY equals the cursor's, by row id, skipping rows whose stored provider id the server does not match; `ingest_state` stays worker-only. Gmail is reported to leave the SELECTED folder's own label out of X-GM-LABELS — immaterial for All Mail (no label of its own); the hub ORs the folder in regardless (§4.4).

**Drafts — the deliberate two-tier exception (ruling 2026-10-11).** A draft — a message flagged `\Draft`, or (X-GM-EXT-1 servers) one carrying the Gmail `\Draft` label — is neither stored nor emitted, in any folder of any mailbox: the one exception to "everything polled is stored". The label is the signal that matters on Gmail: it does **not** set the `\Draft` flag on a draft seen through All Mail (live 2026-10-11 — a test draft reached `mail_messages` with FLAGS `\Seen` and labels `["\Draft"]` under the flag-only guard; fixed the same day). The label rides the same FETCH, so the check costs nothing; both the transport (no body download) and the worker (`isDraft`) apply it. Drafts are unsent (no communication happened; the Apps Script adapter skips them too), and Gmail deletes and re-creates a draft as a new message on every autosave — in All Mail a stream of throwaway UIDs that, stored, would be garbage revisions and orphan-purge noise on every re-key. The UID counts as processed (the cursor passes it), the folder's `ingest_state` counts it (`drafts_skipped_total`), and the transport never downloads a draft's bodies. The message that is finally sent is a new, non-draft message and is ingested normally.

### 4.2 Send
Compose/reply in YC → grant check (`can_send`, on the interactive route per D6 — never inside `emailService`, so automation sends bypass) → `emailService` with the mailbox's `send_credential_id` → existing adapters. With Migadu, one wildcard-send credential per domain serves many mailboxes (convenience, not dependency). After successful send: IMAP APPEND to the mailbox's Sent folder so external clients see YC-sent mail. Guardrails: per-credential daily send budget checked against `email_log` before dispatch (defer + notify on breach — provider counts refused attempts, never retry-hammer); `bulk_ok` flag on credentials; campaign sender refuses non-`bulk_ok` credentials above ~50 recipients.

**As built (S3, 2026-10-11).** `POST /api/mail/send` (staff JWT; SU needs step-up, checked before anything is dispatched; 30 sends / 10 min per user) → `services/mailbox/mailboxSendService.js` → `emailService.sendEmailDirect` with the mailbox's send credential → the existing smtp / gmail adapter. `GET /api/mail/identities` (the From picker) and `GET /api/mail/messages/:id/reply?all=` (reply defaults) beside it. No migration.
- **Grant.** `can_send` via `getAccess` on the route's seat: SU bypass sends; the attorney READ bypass does NOT (the grant row decides — `listSendable` has no role branch); can't read → 404, read-only → 403. `emailService` and the adapters stay grant-blind. A box that cannot send is a 409 with its reason: inactive, no `send_credential_id` (read-only), the credential row gone, a Pabbly credential (no headers, no Cc/Bcc — refused rather than half-sent), or a Google sender whose address is not the box's (`credential_mismatch` — the Gmail API silently rewrites an unrecognized From to the account's primary address, so the mail would leave under another name; a shared SMTP credential stays allowed, the relay decides there).
- **Headers.** `sendEmailDirect` takes HUB-ONLY options — `cc`, `bcc`, `in_reply_to`, `references`, `message_id`, `thread_id` — that the public `sendEmail` strips, and each adapter sets a header only when its option is present: every automation caller builds the same message as before (test-pinned). The adapters still write their one `outbound-*` `email_log` row; the hub writes NO log/timeline row of its own (carry #1: the Gmail box's ingested All-Mail copy, emitted under gmail-firm, is that mailbox's log path; an RFC box's Sent stays store-only — Link to case files it).
- **Reply threading.** The full References header is not stored, so the reply's References is abbreviated (RFC 5322 §3.6.4 allows trimming the middle): `<parent.thread_key> <parent.in_reply_to> <parent.message_id>`, de-duplicated, In-Reply-To = the parent. The worker derives a row's `thread_key` as References[0], so the sent copy lands in the parent's thread (proved through the real derivation on Dovecot — `tests/mailboxS3.dovecot.test.js`). Gmail rewrites the Message-ID of an API send but keeps References; to file the reply in the sender's OWN Gmail conversation the send also passes the parent's Gmail `threadId` (looked up best-effort by the stored `provider_id`, only when the subject is unchanged — Gmail's own rule). SMTP sends get our Message-ID (`<uuid>@<mailbox domain>`). Replies go to From (Reply-To is not stored); a reply to the box's OWN mail goes to that mail's recipients — own = its From is one of the caller's sendable boxes, or the stored row is a Sent copy (`\Sent` label / a Sent folder: mail the account sent under an alias or as automations@). The quote is built server-side from the stored text (`quote_original`, default on).
- **Sent APPEND (carry #2).** Decided per send by the CREDENTIAL: `gmail` (the Gmail API files its own Sent) → never; `smtp` → `imapTransport.appendSent` (the transport's one writer) APPENDs the same MIME (same Message-ID, Bcc kept, `\Seen`) to the box's `\Sent`-flagged folder, else a Sent-named leaf (Sent / Sent Items / Sent Messages / Sent Mail), never creating one — and itself refuses any X-GM-EXT-1 server (a Gmail box sending through an SMTP relay). Recipients the relay refused while accepting others (nodemailer resolves) come back as a `recipients_rejected` warning. No IMAP login, no Sent folder, or an APPEND error → a warning in the response (the mail went out); an error also raises a `mailbox_send_append_failed` warning alert (one per box per day).
- **Read state for the sender (carry #3).** The copy does not exist at send time, so the send schedules a `one_time` `scheduled_jobs` row (`data.type` `mail_sent_read_seed`, first try +6 min, 4 attempts, 300 s doubling backoff) that marks every copy the sender can read — by Gmail id (`provider_id`, probed within a day of the send) or our Message-ID — read through `markRead`. Not stored yet → retry; last attempt → done quietly. Scheduled only when a copy will be stored with a key we know: a Gmail send, or an APPEND into a folder the box polls.
- **Guardrails.** ≤ 10 recipients (To + Cc + Bcc after de-duplication; To beats Cc beats Bcc). Daily budget per TRANSPORT — the account the provider counts against: every gmail credential sharing the Google credential, or one SMTP host+login — counted from `email_log` over 24 h by `source` + every From address that reaches the log through it (aliases and the boxes sending through those credentials), automation sends and FAILED rows included. Default 1500 gmail / 300 smtp, overridable by the `app_settings` row `mail_send_daily_budget` (`{"gmail":n,"smtp":n}`). Breach → 429, nothing dispatched, ONE `mailbox_send_budget` alert per transport per day (`dedup_key`), severity `error` (follow-up 2026-10-12: a spent budget stops every hub send through that account until the window rolls — not a transient blip — and the 429 tells the person IT was told; a warning never emails). Soft: two sends racing at the edge can both pass. Not deferred — the person retries later. `bulk_ok` / the campaign cap are campaign-side and untouched.
- **Send-only identities (S3.1, 2026-10-12, Fred).** A Google account answers to many addresses (every 4lsg.com address is a send-as alias of the account behind mailbox 2, credential 11), but a box is one address. The From picker (`GET /api/mail/identities`) lists real boxes first, then send-only ones, each by address (`send_only` on every row), so a new Compose starts from a real box. Budget, seed and Sent are unchanged: same Google account → same transport, the copy lands in the account's box, found by provider id. Guard (`mailboxService.assertSinglePoller`): no two active, ingest-enabled boxes on one IMAP host + login — a second poller of one account would store, log and fire rules twice; send-only rows naming the account's host/login are allowed.
- **Per-address READING (S3-R, 2026-10-12).** A `can_read` grant on an alias box reads the alias's SLICE of the parent: parent rows the Gmail filter LABELLED for it (`alias_label`, a bound `MEMBER OF` — exact, case-sensitive; catches Bcc and list mail) OR carrying the alias address in From/To/Cc (LIKE narrows, a pinned case-blind REGEXP decides — a superstring address or the address quoted inside a display name never matches). `in_inbox` never applies to a slice (live: the filters label-and-archive — every it@ row has `in_inbox` 0); within the slice the alias's OWN mail — its address is the From — is its Sent and everything else its Inbox (review 2026-10-12, replacing the spec's "`\Sent` = Sent": every send-as address of the account is `\Sent` to Gmail, so the automations@→it@ digests and stuart@→it@ notes are `\Sent` copies that are INCOMING to it@ — live 3 of the first 15 it@ rows, and every digest after; the From rule is S3.2's "own mail is judged against the identity", files a SiteGround parent's Sent-folder and pre-S2-L rows the same way, and puts no row in both scopes). The summary row for an alias carries the slice's Inbox counts — the sidebar badge now counts an alias reader's mail; the totals (badge, All mail, picker) skip an alias whose parent is in the same set, as the list does (else a parent reader's badge double-counts and keeps archived slice rows "Mark all read" on All mail cannot clear). Grants on alias boxes were held back until this shipped and are ordinary grants from day one (ruling 2026-10-12: capability + validation in one deploy, no inert-grant window; no guard was ever written). - **Transactions.** None: the dispatch is the only side effect and nothing of ours is written before it; the tail (email_log id lookup, APPEND, seed row) is best-effort and post-dispatch. Never retried in-process.
- **Audit.** `admin_audit_log` tool `mail_send`: sent / refused_budget / send_failed / rejected_no_elevation, with box, parent, recipient COUNT, email_log id, append outcome — never bodies or addresses.

### 4.3 Read state — per-user by necessity
IMAP `\Seen` is per-MAILBOX; our model is many users per mailbox, so server flags cannot represent "has Fred read this." Per-user read state lives in `mail_read_state` (YC-side). Server flags mirror into `mail_messages.flags` read-only and change only on explicit action (flag/unflag, mark-answered on reply). v1 does NOT write `\Seen` back — avoids two-way sync fights while SB/SS still use external clients.

**As built (S2):** row present = read. Writes are idempotent (`INSERT … ON DUPLICATE KEY UPDATE` / `DELETE` no-op). Opening a conversation marks every unread COPY of every message shown read in one bulk call (`POST /api/mail/read {ids}`); "Mark all read" is the same route with `{all:true, mailbox_ids?, filters?}` and marks exactly what the list would show for that scope, every page — the same predicates (`scopeWhere`: the Inbox — `in_inbox`, §4.4 — unless `all_folders`, plus the filters), never the mailbox behind a filtered list; the pane confirms first (per-user state, no undo). Both are grant-scoped inside the statement (`mailbox_id IN` the readable set). Unread counts are per user over the Inbox only (`in_inbox`, §4.4) — a Sent copy is mail the box itself sent.
