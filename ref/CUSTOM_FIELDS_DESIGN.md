## 1. Decision

One `field_defs` registry as the single source of truth for admin-defined fields; values in one JSON column per entity; a **typed VIRTUAL generated column per active field** as the SQL surface; "promotion" of a hot field = adding an index to its virtual column, nothing more.

Expands the plans.md YC3 line: *"Tenant-defined fields: JSON column + field-definitions table + indexed generated columns for hot fields. Never EAV."*

Rejected permanently: EAV, preallocated slot columns, runtime DDL for real data columns, user-defined entities, Clio-style field-set/matter-template layers (`show_when` on a def replaces structural grouping).

## 2. Architecture

**`field_defs` registry** (sketch — S1 finalizes DDL):
`id, entity ('case'|'contact'|…), field_key, label, field_type, options JSON, validation JSON, show_when JSON, indexed TINYINT, sort_order, active, created_at, updated_at`
(No `sensitive` flag in v1 — see Policy wiring below, revised after the 2026-09-24 SSN ruling.)
Open vocabulary, app-level validation (sql_mode is non-strict — same posture as `contact_roles`). Config versioning rides the YC3 config-as-data/undo mechanism when that exists; until then defs are rows.

**Storage:** `cases.custom`, `contacts.custom` — `JSON NOT NULL DEFAULT (JSON_OBJECT())`. Multi-select = JSON array (this pattern retires the `SET`-type and comma-string problems).

**SQL surface (load-bearing, not convenience):** a reconciler (`services/fieldDefReconciler.js`, S3) maintains, for every active def, a VIRTUAL generated column named exactly `field_key`, typed, string types declared `COLLATE utf8mb4_general_ci`. Three reasons it's mandatory:
1. **Raw-SQL consumers** can't go through an accessor: `report_definitions.sql_text` (staff + AI report builder), sequence `checkCondition`, portal cards SQL mode, RO-key holders. `query_db`'s identifier regex (`^[\w.]+$`) and the resolver's `^\w+$` check (resolverService ~:476) can only express column-shaped references.
2. **Collation semantics:** `custom->>'$.k'` compares as `utf8mb4_bin` (case-sensitive), and adding a matching functional index can silently flip results via optimizer substitution (measured: 1 row with index, 0 rows with IGNORE INDEX, same data — reproduced on 8.4.11, and ALSO for a `CAST(JSON_UNQUOTE(JSON_EXTRACT()))` column; a `JSON_VALUE(… RETURNING …)` column is not substituted: 0/0). The declared-collation column is the only stable comparison surface (1/1 in every variant) — and the reconciler builds its columns with `JSON_VALUE` so its own indexes can't flip a raw query.
3. **Policy enforceability:** the report validator's identifier scan blanks string literals (`stripLiterals`, lib/reportSchema/validator.js) — a JSON path inside a literal is invisible to any denylist; a virtual column name is a bare identifier the scan sees. Any per-field policy YC ever wants (denylist entry, masking) is only enforceable in raw SQL against a column-shaped name. (Revised 2026-09-24: the SSN ruling shrank the denylist to credential material, so today this reason preserves the *option* — reasons 1–2 carry the design on their own.)

**Promotion = `indexed = 1`** on the def; the reconciler adds a secondary index on the virtual column (lookup measured ≈ real column, 0.27 ms vs 386 ms unindexed full scan @ 500k rows). Never a data move. STORED generated column only for the two verified corners a VIRTUAL can't serve: FK (ERROR 3733) and FULLTEXT (ERROR 3106).

**Type map** (def `field_type` → virtual column type). v1 types as built in S3 (`COLUMN_SPECS`); the rest is design for later types:
| field_type | column type | expression | note |
|---|---|---|---|
| text, select | `VARCHAR(255) CHARACTER SET utf8mb4 COLLATE utf8mb4_general_ci` | `JSON_VALUE(custom, '$.k' RETURNING CHAR(255) CHARACTER SET utf8mb4)` | select stores option *value*. 255 = `STRING_MAX_LEN`: text values and option values are capped to it at write / def time (a longer value would read back NULL from the column) |
| number | `DECIMAL(18,4)` | `JSON_VALUE(… RETURNING DECIMAL(18,4))` | `NUMBER_ABS_LIMIT` keeps writes in range |
| date | `DATE` | `JSON_VALUE(… RETURNING DATE)` | |
| boolean | `TINYINT(1)` | `JSON_VALUE(… RETURNING UNSIGNED)` | JSON true → 1, false → 0 |
| multiselect | `JSON` | `JSON_EXTRACT(custom, '$.k')` | query via `MEMBER OF` — case/byte-sensitive, hence values ≠ labels. **Never indexed** (a plain index on JSON is ERROR 3152; a multi-valued index is a later idea) |
| *url, currency, datetime* | *VARCHAR / DECIMAL / DATETIME* | | *not v1 types* |
| *contact_ref* | *INT UNSIGNED* | | *not v1; app-level integrity (twin-column precedent); STORED+FK only if ever proven needed* |

Why `JSON_VALUE`, not the `CAST(JSON_UNQUOTE(JSON_EXTRACT()))` first sketched (measured, §8): the CAST form reads a junk number as **0.0000** (indistinguishable from a real zero), reads JSON `true` as **0** for a boolean, and keeps the substitution hazard above; `JSON_VALUE` returns NULL for missing *and* unconvertible values, with no warning, and never errors under strict mode either (the CAST form's index build fails under strict).

**Row-size budget:** virtual columns count toward InnoDB's 65,535-byte row limit (ERROR 1118 at ADD). Measured headroom at `VARCHAR(255)` utf8mb4 (1,022 bytes each): **~47 string fields on `cases`, ~58 on `contacts`**; number/date/boolean/JSON columns cost almost nothing. A string field past the budget fails its reconcile with an alert.

**Policy wiring (revised 2026-09-24):** `field_defs` v1 carries **no `sensitive` flag**. The SSN ruling showed "sensitive" had no stable meaning here — staff see everything (Form 121; staff read SSNs all day), and the report denylist shrank to credential material only. What actually stays closed is closed for *structural* reasons, each owned by its own mechanism: portal cards' deny-by-default whitelist (values reach a **client** browser), the domainEvents scrub list (envelopes persist independently of the row), the external-forms prefill ceiling (public endpoint). Custom fields join those structures, not a secrecy tier: raw `custom` goes on the domainEvents scrub list and the report/resolver denylists **as a column name** — the bag never travels whole; only named `cf_` columns do — and nothing custom is portal-visible in the pilot. Per-field policy flags (`portal_visible`, `mask_default`, a real staff-secrecy tier) are added only when a demonstrated need defines their semantics — the plans.md inner-platform guard. What survives unchanged: registry-driven lists replacing hand-kept ones (the same field list is hand-kept in ~10 places today, with live drift: `updateCase` blocks only the PK; the two contact ALLOWED lists coincide only by discipline; S2 makes the fn lists registry lookups).

## 3. Rules (invariants — write code against these)

- **Nothing anywhere compares on raw `custom->>'$.k'`** — only the named virtual column (or the write chokepoint).
- Write per key with `JSON_SET(custom, '$.k', ?)` composed into the **same UPDATE** as core columns; never read-modify-write the whole bag (concurrent form save + executor write would lose one).
- Never store JSON null (`->>` returns the string `'null'`); clearing a field = `JSON_REMOVE`.
- `changes` emitted per field key, never on the bag (`_diffNorm` does `String(v)` → `[object Object]`).
- Raw `custom` is excluded from envelopes (domainEvents scrub list), resolver, and reports **always** — the bag never travels whole; only named `cf_` columns do. No per-field exclusions in v1 (§2 Policy wiring). Note `SELECT *` includes virtual columns, and every active def widens every `SELECT *` (envelope size, AI-consumer tokens); acceptable, monitored.
- Namespace: `field_key` matches `^cf_[a-z][a-z0-9_]{1,56}$` (60 chars max — tightened in S3 so the index name `idx_<key>` fits MySQL's 64-char identifier cap); collision with any real column rejected at def creation (information_schema check). `cf_` is reserved.
- **Same `field_key` on both entities is allowed** (UNIQUE is `(entity, field_key)`; ruled 2026-09-24). Unqualified references in a join fail loudly (ERROR 1052); the only silent exposure is an ad-hoc `SELECT *` over cases⋈contacts, where mysql2 keeps the last same-named column — no app query does this (every SQL literal scanned 2026-09-24).
- **`field_type` locks once any record holds a value** for the key (ruled 2026-09-24; enforced from S2). No exceptions, not even → text: storage keeps the old JSON type, and every report/trigger comparison flips to string semantics (`'100' < '9'`). Escape hatch: a new field + one UPDATE copying values — never a hand edit of `field_type`. Free before data exists.
- **Options** (ruled 2026-09-24; enforced from S2): labels and order edit freely; add anytime; an option's `value` freezes once any record holds it (stored identity, like the key). Removal = hard delete if unused, else **retire** (`active: false` on the option — hidden from pickers, still labels existing records, reactivatable; the calendar-types delete-at-zero-refs precedent). Writes accept active *or* retired values and reject unknown ones — rejecting retired would force a read-before-write (a multiselect re-saved with a retired member) and break the one-UPDATE write rule. (Corollary, accepted: an automation can also put a retired value on a record that never had it — pickers hide retired, the API does not; tightening that needs the same read-before-write, so it stays unless it bites.)
- Validation is app-level from the def. `CHECK (JSON_SCHEMA_VALID(...))` DOES throw under non-strict (verified) but altering it is ALGORITHM=COPY — deferred; at most a coarse invariant (custom is an object).
- **`validation.required` is a RENDERER rule, never a chokepoint rule** (S4). The chokepoint must accept a partial patch that omits a required key — otherwise every automation, every aggregate form save and every API caller breaks the moment an admin ticks Required. It is enforced where a human is filling the field in: `public/js/yc-custom-fields.js` blocks its own save.
- **`show_when` v1** (defined S4, evaluated client-side only): exactly one condition object, `{field, op, value}`, `op ∈ eq|ne|in|not_empty|empty`, `field` a same-entity core column or a `cf_` key, `in` takes a NON-EMPTY array, the two empties take no value, and every value must be a SCALAR (a later vocabulary is likeliest to arrive by enriching that slot — `value: {ref: …}` — and v1 must refuse the whole condition rather than String() it into `[object Object]`). No and/or, no nesting. Comparison follows `services/hookFilter.js` — the house's existing condition vocabulary, so there is ONE mental model — with two refinements: a **boolean** source compares as a boolean (`value: 1`, `true` and `'true'` all match a stored Yes), and a **multiselect** source tests MEMBERSHIP (the string form would compare against the comma-joined list, which is a trap). **Anything not exactly this shape is stored untouched, treated as "always show", and console-warned** — strictness is the point: a later v2 vocabulary must not be half-evaluated by v1 and silently hide fields. The `caseconfig/fields.html` builder round-trips a v1 condition and OMITS `show_when` from the PATCH for a stored shape it can't represent (the S1 "an API-set value survives an edit" contract, narrowed to where it still matters), showing it read-only and saying so; an `in` list is entered ONE VALUE PER LINE, never comma-separated (an option value is opaque free text and may contain a comma), and an incomplete condition is refused inline rather than silently clearing the stored one. **A required field hidden by `show_when` is NOT enforced** — visible-and-required only; the alternative is an unsaveable record whose blocking field is off screen. `show_when` is display, not policy: the value still rides the API payload and is still queryable.
- **`case.updated`'s `data` must carry POST-write cf_ values, IN THE COLUMN'S SHAPE** (fixed S4). Two bugs, one fix. (a) `data` is `{...priorRow, ...safeFields}` and cf_ values live in `custom`, which is never overlaid — so `data.cf_x` was the value from BEFORE the write while every core column was post-write, and `contact.updated` (a post-commit `SELECT *` re-fetch) disagreed. (b) The obvious repair — overlay `customSets` — trades that for a worse one: it puts the **JSON-shaped** value in `data` (`1234.5`, `true`, `'2026-09-25'`) while contacts carry the **driver-coerced column** (`'1234.5000'`, `1`, a `Date` → ISO). Measured on 8.4.11, all four types. Conditions compare with `String()` (hookFilter), so `data.cf_rush eq 1` would match on contacts and not on cases. So `updateCase` **reads the generated columns back** after the UPDATE (only the written keys, only when there are any, KEY_RE-guarded, and never fatal — a concurrently-deactivated def may already have lost its column, and the envelope must not take a committed write down with it). The two envelopes are now byte-identical for every type. Core columns are deliberately NOT re-read: that would change `data` for every existing rule, which S4 has no mandate for. `changes.cf_x.to` carries the JSON value and was correct on both sides throughout.
- Reconciler: idempotent diff of defs vs information_schema (defs read fresh under the lock, never from the cache). **ADD VIRTUAL is `ALGORITHM=INSTANT`; DROP COLUMN is `ALGORITHM=INPLACE, LOCK=NONE`** — INSTANT drop is refused (1845) unless the column is the table's last (true on 8.4.11 *and* 9.6.0; the earlier "70 cycles" only ever dropped the tail), while INPLACE drop of a virtual column is metadata-only: no rebuild, `TABLE_ID` unchanged. Neither spends instant-DDL row versions. Indexes: `CREATE`/`DROP INDEX … ALGORITHM=INPLACE LOCK=NONE`, dropped before their column. Every statement spells its algorithm so the engine errors rather than fall back to a table copy. Each ALTER takes a brief exclusive MDL, so the reconciler runs with `lock_wait_timeout = 5` (global is a year) + one retry, on one connection, never in a transaction. Dropping a virtual column destroys no data (values live in JSON) — versioned-undo survives. The diff covers column **type** (COLUMN_TYPE + collation + the expression's function and path), not just existence — a pre-data `field_type` change on an active def retypes its column. Managed = `cf_` name AND `EXTRA = 'VIRTUAL GENERATED'`; any other `cf_` column (real, STORED, hand-made) is never touched or dropped.

## 4. Fences

- **No completion semantics, companion dates, reminders, or stage gating in `field_defs`, ever.** That accretion is how Clio got its field-set layer. Trackers belong to checklists/`pipeline_stage_requirements`. The fence is behavioral, not numerical — the true-custom count drifting up is fine; one tracker sneaking in is not.
- Flat per-entity namespace; conditional display is `show_when` on the def.
- No user-defined entities (fixed entity set + custom fields covers the customizable-CRM goal; revisit only with a real need).
- `contact_roles.attrs` / `attrs_schema` stays exactly as-is; folding role attrs into the registry is a later question.
- **Integration/sync state is not a custom field.** Test: does the column carry concurrency semantics (conditional claim-writes, deliberate timestamp handling)? The Google sync trio (`contact_google_resource_name/_etag/_synced_at`) fails the test — `_persistLink` deliberately doesn't bump `contact_updated` (that's what terminates the drift sweep) and the reconcile-linker does a conditional claim-write. Those belong to the driver/external-refs layer. The pilot's Clio IDs are *passive* refs — acceptable as custom fields now, **graduate to `external_refs` in v3** (recorded so pilot success isn't read as "integration refs are custom fields forever").

## 6. Tenancy & engine posture

Per plans.md (2026-09-14): multi-tenancy is a v3 maybe, **lean DB-per-tenant**, hold on tenant_id columns; **MySQL stays**. This design is engine-neutral and tenancy-neutral, and DB-per-tenant removes the fragile parts (shared index budget, facade views, cross-tenant `cf_` collisions). Per-tenant defs/columns/RO keys come free.

## 8. Measurements (local 8.0.46 @ prod sql_mode, 500k rows, 100 tenants × 5k — 8.4 re-run below)

| Operation | median |
|---|---|
| tenant-scoped JSON equality, no index (5k rows) | 3.8 ms |
| tenant-scoped JSON date range, no index | 6.6 ms |
| tenant-scoped sort on JSON date | 4.8 ms |
