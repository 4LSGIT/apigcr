### Proposed — ratify at review

- **P2 — Bucket** `lsg-yc-comms-archive` (matches `lsg-yc-migration`), us-east1, spec in §4. (F1: name ratified 2026-10-13.)

- **P6 — Scope rules (Option A — R5):** archive every non-suppressed recording and MMS file; transcribe call recordings with ≥ 15 s of AUDIO (measured from the archived file's header — the call clock includes ringing, §6.3) and every voicemail; summarise ≥ 30 s; never transcribe numbers on `comms_no_transcribe` (audio still archived; list maintained by SU / SS — R9).

The table has no action column: the action and `comms_media.id` go in `details` (the `grant_create` / `mint` precedent), the outcome in `status`, and `route`/`method` are NOT NULL — the `reqMeta(req, tool)` pattern in `routes/api.phoneComms.js`.

## 1. Goal

Nothing the firm said or received on a call or in a picture message is lost to a vendor's retention, and anyone entitled to a call can read what was said, see a summary that pulls out what a bankruptcy file needs, and listen to check it — from the Comms hub, the client's case and contact pages, and the Documents tab.

Non-goals: live / in-call transcription; auto-created tasks or deadlines; replacing the phone systems' own recording.

## 3. Architecture

```
TIER 1 (exists, unchanged)        ARCHIVE (this design)                   DERIVED TEXT (this design)
phone_event_log  ──┐
log.log_data       │  comms_archive_sweep (every 2 min)
 .attachments ─────┼─► fetch via adapter ──► gs://lsg-yc-comms-archive ─┐
                   │   (RC cred 9 / Quo cred 10)   + comms_media row      │
                   │                                                      ▼
                   │                         comms_transcribe_sweep ─► STT vendor ─► comms_transcripts
                   │                                                      │            (segments, FULLTEXT)
                   │                                                      ▼
                   │                         comms_summarize_sweep ──► aiService (Sonnet 5.5) ─► summary JSON
                   │                                                                 (grounding check)
                   ▼
SURFACES (grant-checked via mailboxService):  Comms call bubble · MMS in sms bubbles · case/contact
log entries · Documents tab · transcript search.  Bytes: V4 signed URL (5 min) after the check.
```

Boundaries:
- **Tier 1 stays the truth for "a call happened."** `phone_event_log` and the `log` row are never deleted or rewritten by this arc. Purge removes content, not the record of the call.
- **Archive = bytes + registry.** `comms_media` says what we hold, where, its hash, and its state. One row per archived file.
- **Derived text = `comms_transcripts`,** one row per transcribed recording, keyed to its `comms_media` row.
- **Provider specifics live in the phone adapters** (`services/adapters/phone/ringcentral.js`, `quo.js`), which gain fetch functions (§6.1). The archive service never builds provider URLs itself.

## 4. Storage

**Bucket `lsg-yc-comms-archive`** (P2):
- Location `us-east1` (same as Cloud Run and Cloud SQL). Default storage class **Archive** (R2): $0.0012/GiB-month, $0.05/GiB retrieval, 365-day minimum, millisecond access (no restore wait).
- Uniform bucket-level access; public access prevention **enforced**.
- **Soft delete 30 days** (allowed 7–90; 0 disables). A soft-deleted object cannot be permanently removed before its window ends; the policy in force at deletion time applies to it.
- **No retention policy, no Bucket Lock, no lifecycle delete rule, versioning off.** "10 years" (R1) is the absence of deletion, not a rule that forbids it (P3).
- Encryption: Google-managed. CMEK not proposed.
- IAM: runtime SA `618099140949-compute@developer.gserviceaccount.com` — `roles/storage.objectUser` on this bucket only: `storage.objects.create`, `get`, `list`, `delete`, `update`, `move`, `restore` (plus multipart uploads) — the narrowest predefined role with create + get + list + delete; `objectAdmin` adds only object IAM and `setRetention`. The archive sweep's pre-flight requires create, get and list (list for stat-first by prefix); purge needs delete. `roles/iam.serviceAccountTokenCreator` on itself, and the IAM Credentials API, for V4 signing (P5). If GCP STT is chosen, the Speech service agent gets object read on the bucket.
- Infra: `scripts/commsArchive/s0_infra.sh` (Cloud Shell; stages `precheck`, `bucket`, `iam`, `env`, `verify`, `status`, `rollback`; dry-run harness in `s0_harness/`). Result in `ref/INFRA_GCP.md`.

**Object names carry ids only** — no names, numbers or dates beyond year/month — so a leaked listing reveals nothing:

|---|---|

## 5. Schema (S1 and S2 built)

Defaults follow `ref/SCHEMA_CONVENTIONS.md`: no `DEFAULT CHARSET` without `COLLATE` (`comms_media` states `utf8mb4_general_ci` explicitly), vocabularies are app-validated `VARCHAR`, every table and non-obvious column carries a COMMENT. Columns sized to what writes into them (non-strict `sql_mode` truncates silently).

`comms_media` keys to note: one row per file, unique on `(source_table, source_id, kind, part)`; `part=''` is a placeholder (a `tsi:` call before recovery). **Discovery tests existence on `(source_table, source_id, kind)` regardless of `part`** — recovery rewrites the placeholder's `part`, so the unique key alone would re-insert a placeholder every tick. `captured_at` is the call clock (§6.1). `attempts` counts provider-side failures only; `next_attempt_at` doubles as the per-row lease.

```sql
-- S1 (built): comms_media — ref/migrations/2026-10-14_comms_media.sql. Its column
-- COMMENTs are the contract and flow into ref/database.sql; not restated here.

-- S2 (built): comms_transcripts + comms_stt_jobs + comms_no_transcribe —
-- ref/migrations/2026-10-14_comms_s2_transcripts.sql, applied by the session
-- script scripts/commsTranscribeS2Migrate.js (it also re-comments comms_media).
-- Their column COMMENTs are the contract and flow into ref/database.sql.
```

`comms_transcripts` keys to note: one row per transcribed archive item (`call_recording` or `voicemail`), unique on `media_id`; `phone_event_id` is NULL for an RC voicemail (no call row). The contract lane D and the surfaces read: `media_id`, `state`, `segments` `[{s, a, b, t}]` (`s` = `A`, `B`… diarized or `ch1`, `ch2`… multichannel; `a` / `b` start / end in seconds), `full_text` (one line per segment). **No visibility of its own:** every reader JOINs `comms_media` (`restricted`, `channel_id`) — Restrict hides derived text by the parent's flag, never a copy (R9) — and the read-only SQL endpoint may not read it at all (`lib/sqlGuard` SECRET_TABLES, with `comms_no_transcribe`). `attempts` counts TRANSPORT failures (vendor 5xx / network); `next_attempt_at` is the lease and the poll schedule. **`stt_cost_cents` = the row's total STT spend:** the sum of every vendor job ever submitted for it in `comms_stt_jobs` (resubmits, failed jobs and the sample variant included) — a job's billed cost once completed, its estimate until then; kept in step with the ledger and never cleared (cost is not content: purge leaves it). S4's health read reports the ledger's month-to-date figure instead (`commsTranscribeSweep.monthToDateCents` — the one the monthly cap compares).

`comms_stt_jobs` — **one row per POST, WRITTEN AHEAD of it** (`unknown`, with `url_sha256` = sha256 of the signed URL it sends — never the URL; one freshly signed URL per POST, the sample variant's TTL 1 s shorter so its URL is its own) and resolved from the answer (`post_status` = the HTTP status, 0 = none, NULL = the process ended mid-POST): accepted → `submitted` → `completed` / `error` / `lost`; an unreadable 2xx → `drift` (with the id if one came back, else it stays `unknown`); no answer or 502 / 503 / 504 → stays `unknown` (searched for); a definite refusal (4xx, 500) → `refused`, estimate 0. A process that dies mid-POST leaves the `unknown` row, so the spend and the search survive it. It is the money (the monthly cap sums every job by `submitted_at`, whatever its transcript row did since), the owed-delete list (a job with a ref, not `deleted_at`, and not the live job of a `transcribing` row is owed a vendor DELETE until the vendor confirms), and the job-failure count (a row's `main` jobs in `error` / `lost` / `drift` / `unknown`). Ids and money only — readable on the RO endpoint for monitoring.

States, `comms_transcripts`: `pending` (discovered; due to submit) → `transcribing` (a vendor job in flight) → `transcribed` (S3 moves it to `summarized`); `skipped` with `skip_reason` `restricted` (back to `pending` once unrestricted) / `short` / `no_transcribe` / `over_cap`; `failed` (3 main jobs ended `error` / `lost` / `drift` / `unknown`, or still failing transport 30 days after a vendor outage); `purged` (§8 — the fence).

States, `comms_media`:
- `pending` — known work, not yet fetched. Includes rows the sweep cannot fetch for an our-side reason, with `last_error` saying why (`no_line`: the call's line is not a `phone_lines` row — 6 h backoff, no attempt charged, heals itself once the line is added).
- `archived` — bytes in the bucket, `sha256` and `bytes` recorded.
- `none` — the provider has no file after the wait window (Quo staff lines often record nothing; an RC `tsi:` call whose call-log lists no recording 24 h after the call; a Quo call whose well-formed recording list is `data: []` 24 h after the call, or whose recording status is `absent` / `failed`, or `stopped` without a URL once the call is 24 h old — before that it is held as not-yet). A Quo voicemail lookup that keeps answering 404 for 7 days counted from the LATER of the call and the row's first check (the 404 is held — uncharged, re-checked daily — before it counts, so a wrong reading of the undocumented 404 is caught before anything goes terminal, even for calls already old at go-live). Never reached from a response that does not match the provider's documented shape — that is drift (§6.1).
- `gone` — the provider returned not-found for the CONTENT of a file it had listed, on a call at least 24 h old (past RC's 90 days, or deleted at the source); a younger call's 404 is "not yet" and retries. A call-log 404 is not `gone`. The cliff guard exists to keep this at zero.
- `failed` — terminal, by one of two routes (§6.1 step 5); alerts. CLIFF kind (RC call recordings): still not archivable (provider-side failures, `no_line`, an unmatched call-log) when the call passed 90 days on the call clock, so the file can no longer exist at RC — exhausting the attempt count alone does NOT make it `failed`. NO-CLIFF kinds (MMS, Quo recordings): still failing 30 days after the attempts ran out, or waiting uncharged (`no_line`, drift, Quo "not yet") 30 days after the row was created.
- `purged` — §8.

## 6. Pipeline

### 6.1 Archive sweep — `comms_archive_sweep` (S1)

Recurring `scheduled_jobs` row (`type:'recurring'`, `data:{type:'internal_function', function_name:'comms_archive_sweep'}`, `max_attempts` 1 — a throwing tick is rescheduled, not ended), every 2 minutes; seeded by Part B of `ref/migrations/2026-10-14_comms_media.sql`. Code: `services/commsArchiveSweep.js` (tick), `services/commsArchiveService.js` (bucket), `lib/internal_functions/commsArchive.js`. S1a covers RC call recordings; Quo recordings and MMS are S1b.

**Call clock.** `phone_event_log` has no call-time columns: `started_at` / `ended_at` / `recording_id` are `raw_extra` JSON keys (ISO strings ending in `Z`). `captured_at` = `COALESCE(raw_extra.started_at, processed_at)`: the call's start as a UTC `DATETIME` whenever it is present, and ingest time only when it is blank (`tsi:` rows). The start precedes ingest, so an age taken from it is never younger than one taken from ingest time — ages fail safe; discovery order and the cliff guard (§6.2) both use it. (Never `NULLIF(…, '')` the string before the `CAST`: MySQL then types it numerically and every value comes back NULL — the ingest clock everywhere, silently.)

**Concurrency.** Tick lock `GET_LOCK(CONCAT('comms_archive_sweep:', DATABASE()), 0)` on a dedicated pooled connection (released with it in `finally`; the loser returns `skipped:'locked'`) — one writer of the RC Heavy budget across instances and hand runs. Inside it, each row is claimed by a conditional UPDATE lease (`attempts+1`, `next_attempt_at` +10 min); a crashed tick's rows come back when the lease passes.

Kill switch off → only the cliff guard runs. Otherwise each tick, until the 45 s deadline (stop starting work) or the Heavy budget; every RC and GCS call still in flight is bounded by a 3-minute hard deadline (uploads pass a timeout to the library and race a local timer that destroys both streams — the library's simple upload has none of its own), so a stalled GCS cannot hold the tick lock. The upload's bound is the RC fetch's bound plus 5 s, so when RC stalls the body RC's abort lands first and the failure is charged to RC — by design, not timer order. The cliff guard (§6.2) runs on every exit — disabled, locked, pre-flight failure, or a thrown tick:

HEIC, PDF, audio, 3gpp / mp4 / quicktime video, vCard): a listed type is stored as itself; an error-shaped 200 (HTML / JSON / XML) is a provider transient; any other type is evidence and is stored as `application/octet-stream` (`.bin`, never inline), with the provider's claimed type in `last_error`. A generic response type (`octet-stream`) defers to the type the provider's API claimed. Serving stays governed by the separate inline allowlist (§7).
3. **Store.** Only a non-empty 200 whose content-type is on the audio allowlist (`audio/mpeg`, `audio/wav` and aliases) is stored; a 200 carrying JSON or HTML, an empty body, or one whose byte count differs from `Content-Length` is a provider error — the last two abort the upload, and a non-resumable upload whose body errors or ends short commits no object (verified against the real `@google-cloud/storage` 8.1.0 at the S1a review), so adopt only ever sees complete objects. The content fetch sends `Accept-Encoding: identity` (fetch would otherwise decompress a compressed body while `Content-Length` counts the compressed bytes). A failure is charged to whichever stream errored FIRST: the pipeline re-throws a GCS error through the source, so "the source errored" alone would blame RC for a bucket 403. Stream to the bucket with `sha256` computed on the way, `ifGenerationMatch: 0` (never overwrite), then flip the row to `archived` in one UPDATE. **Stat-first:** before fetching, the sweep lists the row's deterministic prefix `phone/rec/<yyyy>/<mm>/<id>-<part>.` (the extension depends on the content-type; yyyy/mm come from `captured_at`, so the prefix is stable across attempts); one object there — left by a crash between upload and UPDATE — is adopted after re-hashing, with no RC call; more than one, or a 0-byte one, is an anomaly (left pending, uncharged, alerted). A 412 on upload (lost race) adopts the same way.
4. **Pacing.** At most `heavy_per_tick` (job param, default and maximum 3 — with calls ≥ 20 s apart and none started after 45 s, a tick cannot deliver more; higher values are clamped) RC Heavy calls per tick, ticks every 2 min: 1.5/min on average. What is guaranteed is the per-tick cap plus the two stops below, not a rolling-minute ceiling — a catch-up tick right after a late one can put 4 calls in one 60 s window, which the 10/min band absorbs (live ingest keeps the rest). On 429: refund the attempt, end the tick (`Retry-After` reported; RC's Heavy window is 60 s, under the tick gap). When RC reports ≤ 4 Heavy calls left in the window, stop after that item. At this pace the backlog measured 2026-10-14 (~2,240 RC recordings under 90 days) drains in ≈ 25 h; the 80–89-day band (~230) in ≈ 2.5 h — inside the cliff, with ~1,000/day of capacity against 21–46/day crossing it.
5. **Retry — charge the side that failed; abandon nothing that can still exist.** (One terminal rule for every kind, `commsArchiveCommon.rowOps().terminalReason`, keyed by kind/provider. RC call recordings are the CLIFF kind, as below. MMS and Quo recordings have no provider retention cliff: a row still failing 30 days after its 8 attempts ran out, or waiting uncharged — `no_line`, drift — for 30 days since it was created, becomes `failed` + error.) Only provider-side failures keep the attempt: RC 5xx / network / timeout, a non-audio or empty 200, a short body → exponential backoff (2^attempts min, capped 60). After 8 the row stays `pending` on a 6 h backoff and alerts at error (repeated failure); it becomes `failed` only once its call is past 90 days on the call clock. A content 404 on a call ≥ 24 h old → `gone`; on a younger call it is a transient (the recording is not ready yet — RC rows are ingested about a minute after the call ends). Our-side failures never spend attempts: the bucket check (config, plus `testIamPermissions` proving create / get / list — no probe write) runs before any row is claimed; the credential's auth check runs before its first claim; a storage error, an RC 401/403 or a 429 mid-tick refunds the attempt and ends the tick — one misconfiguration must not walk the backlog to `failed`.

### 6.2 Cliff guard (S1)

Every tick, on every exit — after the work, and also when the kill switch is off (a paused archive near the edge must still page), when the tick lock is held elsewhere, when the pre-flight fails, or when the tick throws: any non-suppressed RC call row carrying a `raw_extra.recording_id` or a `tsi:` ref, 75–91 days old on the call clock (§6.1; the upper bound keeps calls lost long ago from tripping it forever, and its 1-day margin past 90 keeps it paging through the last day RC might still hold the file), with no `call_recording` row or with any of its rows not `archived` / `none` / `purged` (so `gone` and `failed` rows count) → `alerting.alert` (`source`, `kind`, `group_key` and `title` are required — it throws without them; `severity:'error'`, group `comms_archive_cliff`, `dedup_key` per UTC day; the message carries the count and the oldest age). This is the alarm that matters: past 90 days the loss is permanent. Expect it once on go-live day (the backlog's 75–89-day band is not yet archived); it should be quiet from the next day.

### 6.3 Transcription — `comms_transcribe_sweep` (S2)

Recurring job (`*/2`, Part B of `ref/migrations/2026-10-14_comms_s2_transcripts.sql`). Code: `services/commsTranscribeSweep.js` (tick, purge fence, release), `services/commsTranscribeVendor.js` (AssemblyAI I/O + the pure parser), `services/commsTranscribeAudio.js` (the length estimate), `services/commsTranscribeService.js` (read helpers — `variantSegments` for lane D), `lib/internal_functions/commsTranscribe.js`. Lock `comms_archive_transcribe:<db>`; 45 s deadline; every call bounded.

- **Mode** (`comms_transcribe_mode`): `off` — no NEW submissions; jobs in flight are still polled, stored and deleted (they are paid for and hold a vendor copy), owed deletes still run; `sample` — only the archive items in `comms_eval_items` (lane D's list), the short gate bypassed, `comms_no_transcribe` and both caps honoured, and a 2-channel recording runs BOTH variants (the configured one into `comms_transcripts`, the other as an `stt_raw` child only); `on` — every archived `call_recording` and `voicemail` (MMS audio is not transcribed), newest first so new calls make the same-hour target while the backlog drains behind.
- **Each tick:** pre-flight (settings parse — a bad credential id or gate knob stops the tick, alerted; the credential yields an Authorization header) → poll due `transcribing` rows → orphan search + owed vendor deletes (before any new submit, so a tick a bad POST stops has already paid what it owed) → discover (a `restricted` skip whose item was unrestricted goes back to `pending`) → submit due `pending` rows.
- **Submit gates, in order:** **Restrict** → `skipped:restricted` — a call marked private never leaves our storage (R5's escape hatch; reviewer ruling 2026-10-14); a row restricted while in flight is stored (hidden by the JOIN) and its vendor copy deleted as usual; `comms_no_transcribe` (last 10 digits of `party`) → `skipped:no_transcribe`; the **audio length** estimated from the archived file — a ranged read of its first 8 KB: MP3 frame header (+ Xing / Info frame count when present), WAV fmt / data chunks; `bytes` × 8 ÷ bitrate for CBR (both providers' are), the §2 byte rate if the header is unreadable, drift if neither — which also fills `comms_media.audio_channels`. The call clock is NOT used: it includes ringing (2026-10-14: 268 of 879 archived RC recordings held < 15 s of audio, 4 by call clock). Then a call under `comms_min_transcribe_s` → `skipped:short` (mode `on`, calls only — a short voicemail is still a message); over `comms_stt_max_min_per_call` → `skipped:over_cap` unless released (§6.5); the monthly cap (§6.5).
- **Signing proof:** once per tick, before the first submit, the sweep signs the S0 probe `_s0/probe.txt` (not client data) and GETs it — 200 with its exact bytes — and GETs a copy with one signature character flipped, which must be refused. Until that passes no client audio leaves; a failure is a storage alert, nothing charged.
- **Vendor — AssemblyAI** (P7; credential via `buildHeadersForCredential`): `POST /v2/transcript` with a **1-hour V4 signed URL**, `speech_models ['universal-3-5-pro']`, `language_detection`, `speaker_labels` (diarize) or `multichannel`, `keyterms_prompt` only when the knob is non-empty (+$0.05/h). Polled, not webhooked (no public receiver): re-polled 1, 2, 4… min after submit, capped at 15. Every POST answer after which the vendor MAY hold a job goes into `comms_stt_jobs` (§5). A job `error` or a 404 on poll (the vendor lost it) goes back to `pending` with a fresh URL; 3 such main jobs → `failed`. A POST answered with an unreadable 2xx, or not at all (timeout / network / 502 / 503 / 504), STOPS every vendor call for the tick — a vendor accepting jobs we cannot see is not fed another row — and counts as a failed job (its estimate stays in the spend; any returned id is an owed delete; an id unsafe for a URL is an anomaly for a human). Such a POST's job is searched for in the vendor's list of that UTC day by sha256(`audio_url`) for 24 h — the first matching job the ledger does not already hold (a match that is only ever a known job means the request created none); found → deleted; not found → a warning (the 30-day TTL backstops). One failing search never stops the tick. **Breaker:** when the last 3 POSTs were all uncertain (drift / no answer / 502–504) and the newest is under 6 h old, new submissions pause (error alert `comms_transcribe_breaker`) — each may be a real, billed job. The row goes `transcribing` straight after the MAIN job's answer, before the sample variant's POST, so the live main job is never treated as owed. A 4xx other than 401/403/429 is OUR configuration: tick stopped, error alert, nothing charged. A 401/403 or 429 refunds and stops the tick; a vendor 5xx / network error on a poll backs off on `attempts` (then 6-hourly, `failed` 30 days later) — separately from the job-failure count. A response off the documented shape is drift (parked, alerted) — never "done". Every vendor error text has its URLs' query strings cut (`redactUrls`) before it is stored or alerted.
- **Store:** the vendor JSON with `audio_url` cut to origin + path (the query string is our signature) → `phone/stt/<yyyy>/<mm>/<media id>.<part>.json` (never overwriting: a leftover from a crashed tick is adopted only if byte-identical, else an anomaly) → an archived `stt_raw` row, `restricted` copied from the parent in the same statement → `segments` + `full_text` into the row → `comms_media.duration_s` = the vendor's `audio_duration` (an estimate off by > 20% and > 3 s raises the duration-drift warning). The ledger records the billed cost first, whatever the store does; the vendor copies are then owed deletes, paid the same tick (`DELETE /v2/transcript/<id>` per job, the variant's too), stamped only on a confirmed 2xx / 404, retried with backoff otherwise (an alert after 5 tries); the account's 30-day TTL backstops. A storage failure while storing refunds, alerts and ends the tick.
- **Quo stereo** (`comms_stt_quo_stereo`, default `diarize`; lane D's A/B decides): `diarize` sends the stereo file with speaker labels — AssemblyAI mixes it to one channel (one-channel price, no ffmpeg on our side); `multichannel` transcribes per channel (billed per channel). - **Fallback — Google Chirp 3, dynamic batch** (not built; only if lane D's rubric fails P7): `BatchRecognize` reading `gs://` directly, diarization on, `us` multi-region. Files up to 8 h, but word-level timestamps — which the segment times and Listen-jump need — cap audio at 20 min per file, so calls over ~18 min split into overlapping chunks (ffmpeg) and stitch. ## 8. Restrict and purge

Both limited to SU and SS (Q7 — may widen later), reason required, audited (§7). They are API routes, `routes/api.commsArchive.js`: `POST /api/comms-archive/media/:id/{restrict|unrestrict|purge}` with `{reason}` (1–500 chars) and, for purge, `confirm` equal to the id AND `password` — the caller's own, re-checked by `commsArchiveAdmin.verifyOwnPassword` (bcrypt against `users.password_hash`, the `/admin/elevate` pattern, which SS cannot use: it is SU-only; Fred's ruling, S4). A wrong or missing password is `403` `code:'bad_password'` (never 401 — the shell's `apiSend` answers a 401 with a re-login), audited `rejected_bad_password`, nothing purged and no `attempt` row; five failures in 15 minutes lock purge for that user (429) — each attempt is RESERVED as a failure before bcrypt runs (and released on a right password or a missing hash), so a parallel burst gets at most five guesses per instance; an account with no hash gets `403 no_password`. The UI (S4) is the ⋯ button on each archived item in Comms → Phone, drawn for archive admins (the conversation response's `archive_admin`). **Who (R9, Fred 2026-10-14):** a staff JWT (never an API key) whose user is SU (from `users.user_auth`, not the token) or listed in `app_settings comms_archive_admins` (CSV of `users.user` ids, SU console only, seeded `1` = SS, read uncached, digits only; missing / empty / garbage = SU only) and still `users.user_auth = 'authorized'` (checked per request) — one function, `services/commsArchiveAdmin.isArchiveAdmin`, which the roles arc later swaps for a `users.roles` capability. Every attempt that reaches the router, rejects included, writes an `admin_audit_log` row (`tool='comms_archive'`, `details {action, media_id, reason}`, outcome in `status`); a request without a valid credential is 401'd earlier by `jwtOrApiKey` (logged in `jwt_api_audit_log`). A purge writes an `attempt` row BEFORE the destructive step and its outcome after — if the attempt row cannot be written the purge is refused (503) — and is limited to 20 per user per hour (429, audited).

- **Restrict / unrestrict** — flips `comms_media.restricted` (and hides the derived text with it). Reversible. For "this one is private" without destroying anything.
- **Purge** — irreversible, removes content everywhere we hold it. It runs under the row's sweep lock (`comms_archive_sweep:<db>` for RC call recordings, `comms_archive_media:<db>` otherwise; held → 409, retry), so no tick can be mid-row — downloading or uploading — while it runs. Ordered, idempotent steps (`PURGE_PARTS` in `services/commsArchiveAdmin.js`; S2 and S3 append theirs), then the tombstone; a failed step → 502 and NO tombstone, so the registry never claims a purge that did not happen. A pending row's purge also deletes any object already under its prefix (an upload whose row was never flipped) and stops the row from ever being fetched. What each copy gets:

| Copy | Purge does |
|---|---|
| Bucket: audio / MMS file + `stt_raw` | Delete → soft-deleted 30 days, then gone. Purging an object younger than 365 days incurs the Archive early-delete charge (cents — expected, not an anomaly). For immediate destruction an admin sets soft delete to 0, deletes, restores it (the policy at deletion time applies) — documented runbook, not an app feature |
| `comms_transcripts` | `segments`, `full_text`, `summary`, `summary_text` set NULL; `state='purged'`; `stt_cost_cents` and the `comms_stt_jobs` ledger stay (cost and vendor ids are not content). This is PURGE_PARTS' FIRST step (`transcripts`) because it is the FENCE: the transcription sweep holds its own lock, not the archive lane's, so instead of locking, every sweep write is conditional on the row still being `transcribing` with the job it polled — a write that loses deletes the object it just stored (a failed delete there is an anomaly alert), and an `stt_raw` child inserted before the fence is removed by the next step (`derived_children`). The step also deletes EVERY object under the item's `phone/stt/…/<id>.` prefix by LISTING it (a crash between a put and its child row leaves an object no row names), and the vendor copies of the item's ledger jobs, best-effort: reported in `parts.transcripts` (`deleted` objects; `vendor` `deleted` / `owed` / `none`); an owed delete is retried by the sweep; a job whose POST timed out and was never found in the vendor list cannot be deleted by id — the vendor's 30-day TTL removes it. On a database the S2 migration has not reached, the step is a no-op |
| `comms_media` | `state='purged'`, `purged_at/by/reason`; `object_name` kept so the tombstone says what was removed |
| `ai_calls` (rows in `ai_call_ids`) | `request_excerpt`, `response` set NULL |
| STT vendor | Nothing left: AssemblyAI's copy (and the sample-mode variant's) is deleted right after fetch, a job in flight is deleted by the purge itself (above), and the account's data TTL (30 days, set 2026-10-14; may drop to 7 later) removes anything a failed delete leaves; Google returns results on the job's operation with no separate transcript store (confirm retention of the operation result in S0) |
| Anthropic API | Standard API retention is ~30 days (ZDR is gated opt-in; the newest models are excluded from it) — a purge is complete at Anthropic ~30 days after the last summary attempt. Not trained on without opt-in |
| Cloud SQL backups | Not editable; the content ages out with backup retention (instance setting — F5: the current value stands; record it here during S1) |
| RingCentral / Quo originals | RC deletes at 90 days; Quo — delete in the Quo app if needed. Purge reports this, it doesn't do it |

The `log` row and the `phone_event_log` row stay: that a call happened is the firm's record. Removing those too is a separate, explicit decision outside this design.

**Delete detection (F3):** `comms_archive_verify` (`services/commsArchiveVerify.js`), nightly at 07:15 UTC, stats the `archived` rows whose `id % 7` equals the UTC day number `% 7`, paging through the whole slice until done or its deadline.
