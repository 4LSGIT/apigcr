### Proposed — ratify at review

- **P1 — Own registry tables, not `documents` rows.** `comms_media` (archived binaries) and `comms_transcripts` (derived text), §5. *Why not `documents`:* the documents routes (`/api/documents/*`, including `/:id/raw`) are firm-wide behind `jwtOrApiKey` with no per-user ACL, and the 154k Dropbox rows rely on that. Putting grant-scoped content into that registry means every documents route must learn a source-specific grant check, and any route that misses it serves privileged audio firm-wide — fail-open. The Documents tab still shows archive items (S5), fetched through the archive's own grant-checked API, with the log-style anchoring Fred described (phone / email / docket, resolved at read time, plus manual link).
- **P2 — Bucket** `lsg-yc-comms-archive` (matches `lsg-yc-migration`), us-east1, spec in §4. (F1: name ratified 2026-10-13.)
- **P3 — Deletion posture:** no bucket retention policy and never Bucket Lock; soft delete 30 days; SU Restrict + Purge (§8); delete detection (§10). Replaces the review's first-draft "delete-less service account", withdrawn 2026-10-13: it pushed every purge into Cloud Shell for little protection beyond soft delete + an alarm, and the runtime service account is the default compute SA, which can do everything anyway (`ref/INFRA_GCP.md`).
- **P4 — Sweepers, not ingest hooks.** Recurring internal functions over `phone_event_log`, on the `documents_sync` model: bounded work per tick, fail-closed kill switch read uncached through `settingsService.getSetting`, idempotent on the source row (§6). Phone ingest emits no domain event today, and a sweeper also absorbs provider lag (recordings appear after the call ends) and retries.
- **P5 — Serving by V4 signed URLs** on `storage.googleapis.com`, 5-minute TTL, issued only after the grant check (§7). Needs the runtime SA to sign (`roles/iam.serviceAccountTokenCreator` on itself + IAM Credentials API) — no key file. Fallback if that is refused: an app-origin byte route with Range support under C6.
- **P6 — Scope rules (Option A — R5):** archive every non-suppressed recording and MMS file; transcribe call recordings with ≥ 15 s of AUDIO (measured from the archived file's header — the call clock includes ringing, §6.3) and every voicemail; summarise ≥ 30 s; never transcribe numbers on `comms_no_transcribe` (audio still archived; list maintained by SU / SS — R9).
- **P7 — STT vendor: AssemblyAI Universal-3.5 Pro + diarization** (Fred, 2026-10-13 — F2: same-hour turnaround for +$2.8/month over GCP batch; whole multi-hour files, no chunking; keyterm hints). The no-training opt-out (a free dashboard toggle on paid plans) is set BEFORE the first upload — C7; the vendor-side transcript is deleted right after fetch. S0 validates quality on our audio against the written rubric; fallbacks if it fails: Google STT v2 Chirp 3 dynamic batch (cheaper, up-to-a-day, 20-min chunking), then OpenAI `gpt-4o-transcribe-diarize` (zero vendor retention, ~2× the batch price). Deepgram dropped: v1's claim that its no-training opt-out roughly doubles the price is unsupported by any official page (re-checked 2026-10-13), and its $200 signup credit is one-time, irrelevant to a forever-retention design.
- **P8 — Summary model: Sonnet 5.5 default** (`claude-sonnet-5-5`), with a Haiku 5.5 (`claude-haiku-5-5`) eval in S0. Grounded extraction: every extracted item carries a quote that must occur in the transcript, or it is dropped (§6.4). Nothing auto-creates tasks or deadlines.
- **P9 — Every content access is audited** (view transcript, view summary, listen, open MMS) in `admin_audit_log`, `tool='comms_archive'`. The table has no action column: the action and `comms_media.id` go in `details` (the `grant_create` / `mint` precedent), the outcome in `status`, and `route`/`method` are NOT NULL — the `reqMeta(req, tool)` pattern in `routes/api.phoneComms.js`.
- **P10 — MMS capture rides S1** with recordings (mailbox handover recommendation).

## 1. Goal

Nothing the firm said or received on a call or in a picture message is lost to a vendor's retention, and anyone entitled to a call can read what was said, see a summary that pulls out what a bankruptcy file needs, and listen to check it — from the Comms hub, the client's case and contact pages, and the Documents tab.

Non-goals: live / in-call transcription; auto-created tasks or deadlines; replacing the phone systems' own recording.

## 3. Architecture

```
TIER 1 (exists, unchanged)        ARCHIVE (this design)                   DERIVED TEXT (this design)
phone_event_log  ──┐
log.log_data       │  comms_archive_sweep (every 2 min)
 .attachments ─────┼─► fetch via adapter ──► gs://lsg-yc-comms-archive ─┐
                   │   (RC cred 9 / Quo cred 10)   + comms_media row      │
                   │                                                      ▼
                   │                         comms_transcribe_sweep ─► STT vendor ─► comms_transcripts
                   │                                                      │            (segments, FULLTEXT)
                   │                                                      ▼
                   │                         comms_summarize_sweep ──► aiService (Sonnet 5.5) ─► summary JSON
                   │                                                                 (grounding check)
                   ▼
SURFACES (grant-checked via mailboxService):  Comms call bubble · MMS in sms bubbles · case/contact
log entries · Documents tab · transcript search.  Bytes: V4 signed URL (5 min) after the check.
```

Boundaries:
- **Tier 1 stays the truth for "a call happened."** `phone_event_log` and the `log` row are never deleted or rewritten by this arc. Purge removes content, not the record of the call.
- **Archive = bytes + registry.** `comms_media` says what we hold, where, its hash, and its state. One row per archived file.
- **Derived text = `comms_transcripts`,** one row per transcribed recording, keyed to its `comms_media` row.
- **Provider specifics live in the phone adapters** (`services/adapters/phone/ringcentral.js`, `quo.js`), which hold the fetch functions (§6.1) and declare them as `capabilities.archiveFetch`. The sweeps reach an adapter only through `phoneService.getAdapter` (`commsArchiveCommon.archiveAdapter`), never by requiring it; an adapter that is missing, does not declare `archiveFetch`, or lacks a function the sweep calls stops that provider's archiving for the tick with an `error` alert (`comms_archive_adapter`, one per provider per sweep per day), no row claimed — never a silent skip. The archive service never builds provider URLs itself.

## 4. Storage

**Bucket `lsg-yc-comms-archive`** (P2):
- Location `us-east1` (same as Cloud Run and Cloud SQL). Default storage class **Archive** (R2): $0.0012/GiB-month, $0.05/GiB retrieval, 365-day minimum, millisecond access (no restore wait).
- Uniform bucket-level access; public access prevention **enforced**.
- **Soft delete 30 days** (allowed 7–90; 0 disables). A soft-deleted object cannot be permanently removed before its window ends; the policy in force at deletion time applies to it.
- **No retention policy, no Bucket Lock, no lifecycle delete rule, versioning off.** "10 years" (R1) is the absence of deletion, not a rule that forbids it (P3).
- Encryption: Google-managed. CMEK not proposed.
- IAM: runtime SA `618099140949-compute@developer.gserviceaccount.com` — `roles/storage.objectUser` on this bucket only: `storage.objects.create`, `get`, `list`, `delete`, `update`, `move`, `restore` (plus multipart uploads) — the narrowest predefined role with create + get + list + delete; `objectAdmin` adds only object IAM and `setRetention`. The archive sweep's pre-flight requires create, get and list (list for stat-first by prefix); purge needs delete. `roles/iam.serviceAccountTokenCreator` on itself, and the IAM Credentials API, for V4 signing (P5). If GCP STT is chosen, the Speech service agent gets object read on the bucket.
- Infra: `scripts/commsArchive/s0_infra.sh` (Cloud Shell; stages `precheck`, `bucket`, `iam`, `env`, `verify`, `status`, `rollback`; dry-run harness in `s0_harness/`). Result in `ref/INFRA_GCP.md`.

**Object names carry ids only** — no names, numbers or dates beyond year/month — so a leaked listing reveals nothing:

| Kind | Object name |
|---|---|
| Call recording | `phone/rec/<yyyy>/<mm>/<phone_event_log.id>-<part>.<ext>` |
| MMS file | `phone/mms/<yyyy>/<mm>/<phone_event_log.id>-<part>.<ext>` |
| Voicemail | `phone/vm/<yyyy>/<mm>/<source_id>-<part>.<ext>` — RC: `<RC message id>-<attachment id>`; Quo: `<phone_event_log.id>-<VM id>` |

## 5. Schema (S1, S2 and S3 built)

Defaults follow `ref/SCHEMA_CONVENTIONS.md`: no `DEFAULT CHARSET` without `COLLATE` (`comms_media` states `utf8mb4_general_ci` explicitly), vocabularies are app-validated `VARCHAR`, every table and non-obvious column carries a COMMENT. Columns sized to what writes into them (non-strict `sql_mode` truncates silently).

`comms_media` keys to note: one row per file, unique on `(source_table, source_id, kind, part)`; `part=''` is a placeholder (a `tsi:` call before recovery). **Discovery tests existence on `(source_table, source_id, kind)` regardless of `part`** — recovery rewrites the placeholder's `part`, so the unique key alone would re-insert a placeholder every tick. `captured_at` is the call clock (§6.1). `attempts` counts provider-side failures only; `next_attempt_at` doubles as the per-row lease.

```sql
-- S1 (built): comms_media — ref/migrations/2026-10-14_comms_media.sql. Its column
-- COMMENTs are the contract and flow into ref/database.sql; not restated here.

-- S2 (built): comms_transcripts + comms_stt_jobs + comms_no_transcribe —
-- ref/migrations/2026-10-14_comms_s2_transcripts.sql, applied by the session
-- script scripts/commsTranscribeS2Migrate.js (it also re-comments comms_media).
-- Their column COMMENTs are the contract and flow into ref/database.sql.
```

`comms_transcripts` keys to note: one row per transcribed archive item (`call_recording` or `voicemail`), unique on `media_id`; `phone_event_id` is NULL for an RC voicemail (no call row). The contract lane D and the surfaces read: `media_id`, `state`, `segments` `[{s, a, b, t}]` (`s` = `A`, `B`… diarized or `ch1`, `ch2`… multichannel; `a` / `b` start / end in seconds), `full_text` (one line per segment). **No visibility of its own:** every reader JOINs `comms_media` (`restricted`, `channel_id`) — Restrict hides derived text by the parent's flag, never a copy (R9) — and the read-only SQL endpoint may not read it at all (`lib/sqlGuard` SECRET_TABLES, with `comms_no_transcribe`). `attempts` counts TRANSPORT failures (vendor 5xx / network); `next_attempt_at` is the lease and the poll schedule. **`stt_cost_cents` = the row's total STT spend:** the sum of every vendor job ever submitted for it in `comms_stt_jobs` (resubmits, failed jobs and the sample variant included) — a job's billed cost once completed, its estimate until then; kept in step with the ledger and never cleared (cost is not content: purge leaves it). S4's health read reports the ledger's month-to-date figure instead (`commsTranscribeSweep.monthToDateCents` — the one the monthly cap compares).

`comms_stt_jobs` — **one row per POST, WRITTEN AHEAD of it** (`unknown`, with `url_sha256` = sha256 of the signed URL it sends — never the URL; one freshly signed URL per POST, the sample variant's TTL 1 s shorter so its URL is its own) and resolved from the answer (`post_status` = the HTTP status, 0 = none, NULL = the process ended mid-POST): accepted → `submitted` → `completed` / `error` / `lost`; an unreadable 2xx → `drift` (with the id if one came back, else it stays `unknown`); no answer or 502 / 503 / 504 → stays `unknown` (searched for); a definite refusal (4xx, 500) → `refused`, estimate 0. A process that dies mid-POST leaves the `unknown` row, so the spend and the search survive it. It is the money (the monthly cap sums every job by `submitted_at`, whatever its transcript row did since), the owed-delete list (a job with a ref, not `deleted_at`, and not the live job of a `transcribing` row is owed a vendor DELETE until the vendor confirms), and the job-failure count (a row's `main` jobs in `error` / `lost` / `drift` / `unknown`). Ids and money only — readable on the RO endpoint for monitoring.

`comms_summaries` (S3, `ref/migrations/2026-10-15_comms_s3_summaries.sql`) — the summary WORK QUEUE, one row per transcript, no content: `pending` → `calling` (written ahead of the model call, `est_cents` counted by the cap until `ai_calls` holds the billed cost) → `done` | `skipped` (`restricted` — back to pending once unrestricted — / `short` / `empty` / `refused` / `purged`) | `failed` (3 failed calls). The summary itself is written on `comms_transcripts` (`summary`, `summary_text`, `summary_model`, `ai_call_ids`, `grounding_dropped`, `llm_cost_cents`); `llm_cost_cents` = every `ai_calls` attempt of the row (cumulative; purge keeps it).

States, `comms_transcripts`: `pending` (discovered; due to submit) → `transcribing` (a vendor job in flight) → `transcribed` (S3 moves it to `summarized`); `skipped` with `skip_reason` `restricted` (back to `pending` once unrestricted) / `short` / `no_transcribe` / `over_cap`; `failed` (3 main jobs ended `error` / `lost` / `drift` / `unknown`, or still failing transport 30 days after a vendor outage); `purged` (§8 — the fence). A REDO (§8, S2c-2) sends `transcribed` / `summarized` back to `pending` with its summary cleared, its old text KEPT (hidden by state) and a `comms_redo` marker; a redo that ends `failed` / `skipped` is restored to `transcribed` with that old text. `summarized` → `transcribed` for a summary-only redo.

`comms_redo` (S2c-2, `ref/migrations/2026-10-15_comms_s2c_redo.sql`) — one row per transcript being redone: `transcript_id` (PK), `requested_at` (UTC), `requested_by` (`users.user`), `prev_model` (the old `stt_model` — the submit overwrites it, a restore puts it back). Written in the same transaction as the redo's flip; the transcribe sweep LEFT JOINs it (redo rows submitted first; the old vendor JSON retired only when the new one is stored; main-job failures counted only since `requested_at`; a `failed` / `skipped` marker row restored; the backlog alarm counts a redo from `requested_at`); deleted when the new transcript is stored, by the restore, and by purge. A stale row (a crash between the store and the delete) is harmless — a transcribed row is never submitted. Ids, times and a model name only.

**Schema landmine — `comms_transcripts` cannot be altered in place.** Any ALTER that adds a column (or otherwise rebuilds the table) is refused with `ALGORITHM=INSTANT` and with `ALGORITHM=INPLACE` (`LOCK=NONE` or `SHARED`) — ER 1846 "InnoDB presently supports one FULLTEXT index creation at a time", because the rebuild must recreate `ft_comms_transcripts` (measured on MySQL 8.4.11, 2026-10-15). Only `ALGORITHM=COPY` works: a full copy + FULLTEXT rebuild with every write of both comms sweeps blocked for its duration (and `'off'` modes still poll and write). New per-transcript state goes in a side table keyed on `transcript_id` (as `comms_redo` does), unless a COPY under a write freeze is worth it.

States, `comms_media`:
- `pending` — known work, not yet fetched. Includes rows the sweep cannot fetch for an our-side reason, with `last_error` saying why (`no_line`: the call's line is not a `phone_lines` row — 6 h backoff, no attempt charged, heals itself once the line is added).
- `archived` — bytes in the bucket, `sha256` and `bytes` recorded.
- `none` — the provider has no file after the wait window (Quo staff lines often record nothing; an RC `tsi:` call whose call-log lists no recording 24 h after the call; a Quo call whose well-formed recording list is `data: []` 24 h after the call, or that Quo answers "Call not found" (`404` `0900404`) 24 h after the call, or whose recording status is `absent` / `failed`, or `stopped` without a URL once the call is 24 h old — before that it is held as not-yet). A Quo voicemail lookup that keeps answering 404 for 7 days counted from the LATER of the call and the row's first check (the 404 is held — uncharged, re-checked daily — before it counts, so a wrong reading of the undocumented 404 is caught before anything goes terminal, even for calls already old at go-live). Never reached from a response that does not match the provider's documented shape — that is drift (§6.1).
- `gone` — the provider returned not-found for the CONTENT of a file it had listed, on a call at least 24 h old (past RC's 90 days, or deleted at the source); a younger call's 404 is "not yet" and retries. A call-log 404 is not `gone`. The cliff guard exists to keep this at zero.
- `failed` — terminal, by one of two routes (§6.1 step 5); alerts. CLIFF kind (RC call recordings): still not archivable (provider-side failures, `no_line`, an unmatched call-log) when the call passed 90 days on the call clock, so the file can no longer exist at RC — exhausting the attempt count alone does NOT make it `failed`. NO-CLIFF kinds (MMS, Quo recordings): still failing 30 days after the attempts ran out, or waiting uncharged (`no_line`, drift, Quo "not yet") 30 days after the row was created.
- `purged` — §8.

## 6. Pipeline

### 6.1 Archive sweep — `comms_archive_sweep` (S1)

Recurring `scheduled_jobs` row (`type:'recurring'`, `data:{type:'internal_function', function_name:'comms_archive_sweep'}`, `max_attempts` 1 — a throwing tick is rescheduled, not ended), every 2 minutes; seeded by Part B of `ref/migrations/2026-10-14_comms_media.sql`. Code: `services/commsArchiveSweep.js` (tick), `services/commsArchiveService.js` (bucket), `lib/internal_functions/commsArchive.js`. S1a covers RC call recordings; Quo recordings and MMS are S1b.

**Call clock.** `phone_event_log` has no call-time columns: `started_at` / `ended_at` / `recording_id` are `raw_extra` JSON keys (ISO strings ending in `Z`). `captured_at` = `COALESCE(raw_extra.started_at, processed_at)`: the call's start as a UTC `DATETIME` whenever it is present, and ingest time only when it is blank (`tsi:` rows). The start precedes ingest, so an age taken from it is never younger than one taken from ingest time — ages fail safe; discovery order and the cliff guard (§6.2) both use it. (Never `NULLIF(…, '')` the string before the `CAST`: MySQL then types it numerically and every value comes back NULL — the ingest clock everywhere, silently.)

**Concurrency.** Tick lock `GET_LOCK(CONCAT('comms_archive_sweep:', DATABASE()), 0)` on a dedicated pooled connection (released with it in `finally`; the loser returns `skipped:'locked'`) — one writer of the RC Heavy budget across instances and hand runs. Inside it, each row is claimed by a conditional UPDATE lease (`attempts+1`, `next_attempt_at` +10 min); a crashed tick's rows come back when the lease passes.

Kill switch off → only the cliff guard runs. Otherwise each tick, until the 45 s deadline (stop starting work) or the Heavy budget; every RC and GCS call still in flight is bounded by a 3-minute hard deadline (uploads pass a timeout to the library and race a local timer that destroys both streams — the library's simple upload has none of its own), so a stalled GCS cannot hold the tick lock. The upload's bound is the RC fetch's bound plus 5 s, so when RC stalls the body RC's abort lands first and the failure is charged to RC — by design, not timer order. The cliff guard (§6.2) runs on every exit — disabled, locked, pre-flight failure, or a thrown tick:

1. **Discover.** Insert `pending` rows for:
   - calls in `phone_event_log` (`event_type='call'`, `suppressed=0`) with no `call_recording` row: RC rows carrying a `raw_extra.recording_id` (`part` = that id) or a `tsi:` ref (`part=''` placeholder), younger than 90 days on the call clock — older ones are already gone at RC and are not fetched; Quo rows that were answered — `raw_extra.provider_status = 'completed'` (its only other value is `no-answer`; call duration cannot tell them apart, because no-answer rows carry ringing time too) — get a `part=''` placeholder: Quo rows never carry a recording id, the recording list decides. A Quo call whose `provider_status` is anything else is NOT discovered and raises its own error alert once a day naming the value and count (`comms_archive_quo_status_drift` — a separate group, so a status that stays present cannot hide per-row drift);
   - MMS texts (`event_type='sms'`, `suppressed=0`; suppressed texts have no `log` row) whose `log.log_data.attachments` is a non-empty array: one `mms_file` row per attachment, `part` = the RC attachment id or `q<ordinal>` for Quo (Quo's stored ref is a signed URL only). `log.log_data` is TEXT, so a malformed row is read as no attachments rather than failing the statement, and the per-tick LIMIT counts MESSAGES, so a message's attachments are always inserted together.
   RC call recordings run in `comms_archive_sweep`; Quo recordings and all MMS run in `comms_archive_media_sweep` (`services/commsArchiveMediaSweep.js`, every 2 min, its own lock `comms_archive_media:<db>` and budgets: RC Medium ≤ 6 calls/tick, Quo API ≤ 20 calls/tick — Quo's documented limit is 10 requests/second per key, shared with live sends), so the media work never competes with the cliff.
   Oldest first within RC's window (200 per tick), so the backlog drains toward the cliff, not away from it. The "no row" test is `NOT EXISTS` on `(source_table, source_id, kind)` regardless of `part` (§5); `INSERT IGNORE` on the unique key is only the race backstop.
2. **Fetch.** Through the line's adapter (`services/adapters/phone/ringcentral.js` `fetchRecordingContent` / `findSessionRecordings`, credentials via `buildHeadersForCredential`), resolved through `phoneService.getAdapter` and checked for `capabilities.archiveFetch` in the pre-flight, before any claim (§3). The line → credential path is data: `phone_event_log.line_number` = `phone_lines.phone_number` → `phone_lines.credential_id`; no `phone_lines` row → `no_line` (§5).
   - **RC recording:** recording id from `raw_extra.recording_id`, `media.ringcentral.com/restapi/v1.0/account/~/recording/<id>/content`. For `tsi:` rows, `call-log?telephonySessionId=` with an explicit `dateFrom`/`dateTo` around the call (RC defaults to the last 24 h); only records whose `telephonySessionId` equals the requested one count (if RC ever ignored the filter, other calls' recordings would land under this call's party and line — the grant anchor); records returned but none matching is treated as a shape change, not as "no recording": the row is parked uncharged (2 h) and alerts, and is never marked `none` on that evidence (`none` satisfies the cliff guard); the first listed recording fills the placeholder, any others get rows of their own; nothing listed → retry in 2 h, `none` once the call is 24 h old.
   - **RC MMS:** `media.ringcentral.com/…/account/~/extension/~/message-store/<provider_ref>/content/<attachment id>` (RC Medium group). rc2 (2486213656) is a second number on the main extension: every RC webhook carries `ownerId` 55880693 and rc2's own MMS URIs are under extension 55880693, so `~` serves both lines and no extension id is stored anywhere. A content 404 is `gone` once the message is 24 h old.
   - **Quo recording:** `GET /v1/call-recordings/<provider_ref>` → `data: [{id, url, type, status, duration, startTime}]`, oldest first: the first item fills the placeholder, the rest get rows of their own (`part` = recording id). Per row: `completed` / `stopped` with a URL → download; `in-progress` / `processing` / `paused` / `stopping` — and `stopped` without a URL during the first 24 h after the call (it may be transitional) — → retry in 30 min, uncharged, under the no-cliff terminal rule (`failed` at 30 days), and a call still "not yet" 24 h on raises one alert per day (`comms_archive_quo_not_yet`, warning then error); `deleted` → `gone`; `absent` / `failed` (the docs define them as no recording), and `stopped` without a URL after 24 h → `none`. A list request answered `404` with code `0900404` AND the message "Call not found" (both required — Quo does not know the call, so no recording will ever be listed) on a placeholder → `none` once the call is 24 h old on the call clock (`noneAfterHours`, as for `data: []`), uncharged and never counted as stuck, `last_error 'quo call-recordings 404 Call not found (24 h+) - none'`, counted as `quo_call_not_found` in the tick output; on a younger call → not yet (uncharged, retried in 30 min). Any other 404 shape, and a "Call not found" on a row whose recording was already listed, stays a charged provider failure. A Quo call whose `provider_status` is outside {`completed`, `no-answer`} is not discovered and is raised as drift (once a day, naming the value) — never skipped silently.
   - **Quo MMS:** `GET /v1/messages/<provider_ref>` → `data.media[]` → the matching item's fresh signed URL (the stored link expires and is never reused) and `type`. Matched by the `message-media/<id>` segment of the URL path when the stored link and the fresh items both carry one; by ordinal when neither does; with an id on one side only, by ordinal ONLY when the message stored exactly one attachment and Quo lists exactly one (no mislabel is possible — Quo's June 2026 URL-scheme change left six stored links as `share.quo.com/v1/file/i/<id>.<ext>` or `storage.googleapis.com/opstatics/<hex>`); anything else (one-sided with more than one item, or no fresh item with the stored id) is drift — one file is never archived under another's part.
   - **Quo 401 vs 403 (live 2026-10-14):** a `401` is the CREDENTIAL — the no_auth alert, Quo stops for the tick. A `403` is the RESOURCE: Quo answered `0900403` "You are forbidden to access the requested Call Recordings" for every request on one line (2489655355) while the other lines were fine — Quo forbids per line, not per key. So a 403 parks THAT row uncharged for 24 h (`last_error 'quo 403 <code> on <endpoint>: <message>'`; terminal by the no-cliff rule), the tick continues with every other row and line, and one escalating alert per line (`comms_archive_quo_forbidden:<line>`) names the line, what was refused (recordings / MMS / voicemails) and how many rows wait. Guard: if every Quo request of a tick is a 403 across ≥ 2 lines, the credential no_auth alert is raised too. Applies to `/v1/call-recordings`, `/v1/messages` and `/v1/call-voicemails`. Every 401/403 (both providers) records the endpoint as a path template, the status and the provider's error text in the alert and the tick output.
   - **Signed downloads (Quo):** https only — redirects are followed by hand (at most 3 hops) and a redirect into http is refused — no credential header ever sent to the signed host, `Accept-Encoding: identity`; any error stored or alerted names the URL's HOST, never its query string (the signature).
   - **Voicemails (S1c, R10)** — kind `voicemail`, objects `phone/vm/<yyyy>/<mm>/<source_id>-<part>.<ext>`, no-cliff kind:
     - **RC:** each RC credential in `phone_lines` (data) lists its extension's message-store, `messageType=VoiceMail` (RC Light group, probed 2026-10-14) — STATELESS: the full set from a fixed epoch (2016-01-01), each page call capped at 10 s, ≤ 3 pages (more is drift: > 300 voicemails ever is loud, not silent). With no watermark, a record skipped or drifted is listed — and alerted — again next time. It runs after the tick's row work, on a tick that was DUE at its start: the top of the hour (UTC minute 0–1) OR the last COMPLETED listing is more than 90 min old — read back from `job_results` (the tick's own output `rc_vm_listing = 'complete'`, newest 240 rows of the media-sweep job; no new state), so a :00 tick that started late behind the cliff sweep, ran long, met a held lock or a failed pre-flight is caught up on the next tick. No completed listing in 6 h raises its own alarm. 401/403 on the listing is the credential's (the no_auth alert); listing drift alerts in its OWN group, so it never eats the day's per-row drift alert. Coverage assumption (verified 2026-10-14 via the temp route): the account has ONE active User extension (55880693) — the other extensions (Department 1, Voicemail 2) are NotActivated, plus the company extension — so `~`, the authenticated extension, covers every voicemail; re-check if extensions are activated. Six voicemails exist (2020-10 → 2024-09), all predating phone ingest, so a voicemail is anchored by provider identity: `source_table 'rc_message'`, `source_id` = the RC message id, `part` = the AudioRecording attachment id. `channel_id` = the `phone_lines` row of the number it was LEFT ON (`to[]`), whatever that line's provider is today (2484179800, RC in 2020, is a Quo line now — R6: access follows the line); no to-number (the 2024-09-15 one) → NULL. `party` = the caller, `captured_at` = `creationTime`. Alive and Deleted (in RC's trash, still retrievable) are archived; Purged is skipped. Fetched with the one RC credential in `phone_lines` (more than one → parked + alerted as ambiguous; `ref/plans.md`); content via the message-store content path (RC Medium). A voicemail our registry has PURGED is never touched again — no late transcript is created or fetched under it.
     - **Quo:** one placeholder per Quo call (`completed` and `no-answer` — a call routed to voicemail may report completed) → `GET /v1/call-voicemails/<callId>` (docs only): `data {id ^VM, status completed | in-progress, recordingUrl, duration, transcript}`. `completed` + URL → the VM id fills `part`, then a signed download; `in-progress` → not yet (alerted at 24 h+, `failed` at 30 days); any other shape → drift. What a call WITHOUT a voicemail returns is undocumented — observed live 2026-10-14: `404`, code `1200404`, "Call voicemail not found" (on a call of the 403-forbidden line 2489655355, so read it with caution) — matching the docs reading: a 404 is HELD — its own uncharged park (the attempt refunded), re-checked every 24 h, outside the not-yet alert, `last_error 'quo voicemail: 404 held since <date>, until <date>'` — for 7 days counted from the LATER of the call and the row's first check, then `none`; and until the first Quo voicemail is archived a sanity alarm (`comms_archive_quo_vm_sanity`) reports the counts daily — warning, ERROR once it has persisted 48 h with none found — then goes quiet for good.
     - **Vendor transcripts (C1, R10):** Quo's `transcript` (stored straight after its voicemail's audio) and RC's AudioTranscription attachment (only when `vmTranscriptionStatus` is `Completed`; its own pending row) become kind `stt_raw` objects `phone/stt/<yyyy>/<mm>/<voicemail comms_media.id>.<vendor>.json` (`{vendor, voicemail_id | message_id, transcript, fetched_at}`) with a comms_media row (`source_table 'comms_media'`, `source_id` = the voicemail's id, `restricted` inherited). Secondary to S2's transcript. A transcript problem never parks or charges the voicemail — it is drift at most. Restrict cascades to them; purge removes them with their voicemail.
   - **Shape drift.** The Quo shapes come from Quo's API reference, unprobed. Whatever does not match it — `data` missing or not an array, an unparseable 200, `media` missing, the ordinal absent, an item without an id, a recording id no longer listed, an unknown status, a non-https URL — parks the row uncharged (2 h) with `last_error 'shape drift: …'` and raises one error alert per day (`comms_archive_shape_drift`). It is never read as "no file": `none` satisfies the cliff guard's logic, and a silent drift would lose content with no alarm.
   - **MMS types.** `MEDIA_TYPES` in `services/commsArchiveService.js` decides what is storable (images incl. HEIC, PDF, audio, 3gpp / mp4 / quicktime video, vCard): a listed type is stored as itself; an error-shaped 200 (HTML / JSON / XML) is a provider transient; any other type is evidence and is stored as `application/octet-stream` (`.bin`, never inline), with the provider's claimed type in `last_error`. A generic response type (`octet-stream`) defers to the type the provider's API claimed. Serving stays governed by the separate inline allowlist (§7).
3. **Store.** Only a non-empty 200 whose content-type is on the audio allowlist (`audio/mpeg`, `audio/wav` and aliases) is stored; a 200 carrying JSON or HTML, an empty body, or one whose byte count differs from `Content-Length` is a provider error — the last two abort the upload, and a non-resumable upload whose body errors or ends short commits no object (verified against the real `@google-cloud/storage` 8.1.0 at the S1a review), so adopt only ever sees complete objects. The content fetch sends `Accept-Encoding: identity` (fetch would otherwise decompress a compressed body while `Content-Length` counts the compressed bytes). A failure is charged to whichever stream errored FIRST: the pipeline re-throws a GCS error through the source, so "the source errored" alone would blame RC for a bucket 403. Stream to the bucket with `sha256` computed on the way, `ifGenerationMatch: 0` (never overwrite), then flip the row to `archived` in one UPDATE. **Stat-first:** before fetching, the sweep lists the row's deterministic prefix `phone/rec/<yyyy>/<mm>/<id>-<part>.` (the extension depends on the content-type; yyyy/mm come from `captured_at`, so the prefix is stable across attempts); one object there — left by a crash between upload and UPDATE — is adopted after re-hashing, with no RC call; more than one, or a 0-byte one, is an anomaly (left pending, uncharged, alerted). A 412 on upload (lost race) adopts the same way.
4. **Pacing.** At most `heavy_per_tick` (job param, default and maximum 3 — with calls ≥ 20 s apart and none started after 45 s, a tick cannot deliver more; higher values are clamped) RC Heavy calls per tick, ticks every 2 min: 1.5/min on average. What is guaranteed is the per-tick cap plus the two stops below, not a rolling-minute ceiling — a catch-up tick right after a late one can put 4 calls in one 60 s window, which the 10/min band absorbs (live ingest keeps the rest). On 429: refund the attempt, end the tick (`Retry-After` reported; RC's Heavy window is 60 s, under the tick gap). When RC reports ≤ 4 Heavy calls left in the window, stop after that item. At this pace the backlog measured 2026-10-14 (~2,240 RC recordings under 90 days) drains in ≈ 25 h; the 80–89-day band (~230) in ≈ 2.5 h — inside the cliff, with ~1,000/day of capacity against 21–46/day crossing it.
5. **Retry — charge the side that failed; abandon nothing that can still exist.** (One terminal rule for every kind, `commsArchiveCommon.rowOps().terminalReason`, keyed by kind/provider. RC call recordings are the CLIFF kind, as below. MMS and Quo recordings have no provider retention cliff: a row still failing 30 days after its 8 attempts ran out, or waiting uncharged — `no_line`, drift — for 30 days since it was created, becomes `failed` + error.) Only provider-side failures keep the attempt: RC 5xx / network / timeout, a non-audio or empty 200, a short body → exponential backoff (2^attempts min, capped 60). After 8 the row stays `pending` on a 6 h backoff and alerts at error (repeated failure); it becomes `failed` only once its call is past 90 days on the call clock. A content 404 on a call ≥ 24 h old → `gone`; on a younger call it is a transient (the recording is not ready yet — RC rows are ingested about a minute after the call ends). Our-side failures never spend attempts: the bucket check (config, plus `testIamPermissions` proving create / get / list — no probe write) runs before any row is claimed; the credential's auth check runs before its first claim; a storage error, an RC 401/403 or a 429 mid-tick refunds the attempt and ends the tick — one misconfiguration must not walk the backlog to `failed`.

### 6.2 Cliff guard (S1)

Every tick, on every exit — after the work, and also when the kill switch is off (a paused archive near the edge must still page), when the tick lock is held elsewhere, when the pre-flight fails, or when the tick throws: any non-suppressed RC call row carrying a `raw_extra.recording_id` or a `tsi:` ref, 75–91 days old on the call clock (§6.1; the upper bound keeps calls lost long ago from tripping it forever, and its 1-day margin past 90 keeps it paging through the last day RC might still hold the file), with no `call_recording` row or with any of its rows not `archived` / `none` / `gone` / `purged` (a `failed` row counts — it may still be fetchable; a `gone` row does not — its content is already lost and `comms_archive_gone` alerts on it, so counting it would page every day for content no action can save) → `alerting.alert` (`source`, `kind`, `group_key` and `title` are required — it throws without them; `severity:'error'`, group `comms_archive_cliff`, `dedup_key` per UTC day; the message carries the count and the oldest age). This is the alarm that matters: past 90 days the loss is permanent. Expect it once on go-live day (the backlog's 75–89-day band is not yet archived); it should be quiet from the next day.

### 6.3 Transcription — `comms_transcribe_sweep` (S2)

Recurring job (`*/2`, Part B of `ref/migrations/2026-10-14_comms_s2_transcripts.sql`). Code: `services/commsTranscribeSweep.js` (tick, purge fence, release), `services/commsTranscribeVendor.js` (AssemblyAI I/O + the pure parser), `services/commsTranscribeAudio.js` (the length estimate), `services/commsTranscribeService.js` (read helpers — `variantSegments` for lane D), `lib/internal_functions/commsTranscribe.js`. Lock `comms_archive_transcribe:<db>`; 45 s deadline; every call bounded.

- **Mode** (`comms_transcribe_mode`): `off` — no NEW submissions; jobs in flight are still polled, stored and deleted (they are paid for and hold a vendor copy), owed deletes still run; `sample` — only the archive items in `comms_eval_items` (lane D's list), the short gate bypassed, `comms_no_transcribe` and both caps honoured, and a 2-channel recording runs BOTH variants (the configured one into `comms_transcripts`, the other as an `stt_raw` child only); `on` — every archived `call_recording` and `voicemail` (MMS audio is not transcribed), newest first so new calls make the same-hour target while the backlog drains behind.
- **Each tick:** pre-flight (settings parse — a bad credential id or gate knob stops the tick, alerted; the credential yields an Authorization header) → poll due `transcribing` rows → orphan search + owed vendor deletes (before any new submit, so a tick a bad POST stops has already paid what it owed) → discover (a `restricted` skip whose item was unrestricted goes back to `pending`) → submit due `pending` rows.
- **Submit gates, in order:** **Restrict** → `skipped:restricted` — a call marked private never leaves our storage (R5's escape hatch; reviewer ruling 2026-10-14); a row restricted while in flight is stored (hidden by the JOIN) and its vendor copy deleted as usual; `comms_no_transcribe` (last 10 digits of `party`) → `skipped:no_transcribe`; the **audio length** estimated from the archived file — a ranged read of its first 8 KB: MP3 frame header (+ Xing / Info frame count when present), WAV fmt / data chunks; `bytes` × 8 ÷ bitrate for CBR (both providers' are), the §2 byte rate if the header is unreadable, drift if neither — which also fills `comms_media.audio_channels`. The call clock is NOT used: it includes ringing (2026-10-14: 268 of 879 archived RC recordings held < 15 s of audio, 4 by call clock). Then a call under `comms_min_transcribe_s` → `skipped:short` (mode `on`, calls only — a short voicemail is still a message); over `comms_stt_max_min_per_call` → `skipped:over_cap` unless released (§6.5); the monthly cap (§6.5).
- **Signing proof:** once per tick, before the first submit, the sweep signs the S0 probe `_s0/probe.txt` (not client data) and GETs it — 200 with its exact bytes — and GETs a copy with one signature character flipped, which must be refused. Until that passes no client audio leaves; a failure is a storage alert, nothing charged.
- **Vendor — AssemblyAI** (P7; credential via `buildHeadersForCredential`): `POST /v2/transcript` with a **1-hour V4 signed URL**, `speech_models ['universal-3-5-pro']`, `language_detection`, `speaker_labels` (diarize) or `multichannel`, `keyterms_prompt` only when the knob is non-empty (+$0.05/h), and `filter_profanity: true` on every job (+$0.01/h; Fred 2026-10-15 — the vendor replaces foul words with asterisks, so no word list lives in this codebase; the recording stays the record, and transcripts made before it are masked only when redone). A diarize job carries `speaker_options {max_speakers_expected}` = `comms_stt_max_speakers` when it is above 0 — a HARD cap (seeded 2; set to 0, no cap, by Fred on 2026-10-15 after QA found most 3+ splits were real voices and a cap merges hearings / 341 meetings — §8 `capped` redoes the rows made under it): extra voices merge into existing labels. Without it the vendor allows up to 10 speakers on 2–10 min audio and 30 beyond, and 27% of RC mono calls came back over-split (up to 24 "speakers", 2026-10-15). A cap, not an exact count: one voice (a voicemail, one-sided audio) stays one label, and a real third party merges into one of two — the lesser harm. Multichannel never gets it (the vendor applies the limits PER CHANNEL). Such a row's `stt_model` is tagged `+max<N>` (`universal-3-5-pro+diarize+max2`) so hinted rows can be told apart; every reader keys the variant on `/\+multichannel$/` only. Polled, not webhooked (no public receiver): re-polled 1, 2, 4… min after submit, capped at 15. Every POST answer after which the vendor MAY hold a job goes into `comms_stt_jobs` (§5). A job `error` or a 404 on poll (the vendor lost it) goes back to `pending` with a fresh URL; 3 such main jobs → `failed`. A POST answered with an unreadable 2xx, or not at all (timeout / network / 502 / 503 / 504), STOPS every vendor call for the tick — a vendor accepting jobs we cannot see is not fed another row — and counts as a failed job (its estimate stays in the spend; any returned id is an owed delete; an id unsafe for a URL is an anomaly for a human). Such a POST's job is searched for in the vendor's list of that UTC day by sha256(`audio_url`) for 24 h — the first matching job the ledger does not already hold (a match that is only ever a known job means the request created none); found → deleted; not found → a warning (the 30-day TTL backstops). One failing search never stops the tick. **Breaker:** when the last 3 POSTs were all uncertain (drift / no answer / 502–504) and the newest is under 6 h old, new submissions pause (error alert `comms_transcribe_breaker`) — each may be a real, billed job. The row goes `transcribing` straight after the MAIN job's answer, before the sample variant's POST, so the live main job is never treated as owed. A 4xx other than 401/403/429 is OUR configuration: tick stopped, error alert, nothing charged. A 401/403 or 429 refunds and stops the tick; a vendor 5xx / network error on a poll backs off on `attempts` (then 6-hourly, `failed` 30 days later) — separately from the job-failure count. A response off the documented shape is drift (parked, alerted) — never "done". Every vendor error text has its URLs' query strings cut (`redactUrls`) before it is stored or alerted.
- **Store:** the vendor JSON with `audio_url` cut to origin + path (the query string is our signature) → `phone/stt/<yyyy>/<mm>/<media id>.<part>.json` (never overwriting: a leftover from a crashed tick is adopted only if byte-identical, else an anomaly) → an archived `stt_raw` row, `restricted` copied from the parent in the same statement → `segments` + `full_text` into the row → `comms_media.duration_s` = the vendor's `audio_duration` (an estimate off by > 20% and > 3 s raises the duration-drift warning). The ledger records the billed cost first, whatever the store does; the vendor copies are then owed deletes, paid the same tick (`DELETE /v2/transcript/<id>` per job, the variant's too), stamped only on a confirmed 2xx / 404, retried with backoff otherwise (an alert after 5 tries); the account's 30-day TTL backstops. A storage failure while storing refunds, alerts and ends the tick.
- **Quo stereo** (`comms_stt_quo_stereo`, default `diarize`; lane D's A/B decides): `diarize` sends the stereo file with speaker labels — AssemblyAI mixes it to one channel (one-channel price, no ffmpeg on our side); `multichannel` transcribes per channel (billed per channel). The choice follows the file's header channel count, not the provider.
- **Fallback — Google Chirp 3, dynamic batch** (not built; only if lane D's rubric fails P7): `BatchRecognize` reading `gs://` directly, diarization on, `us` multi-region. Files up to 8 h, but word-level timestamps — which the segment times and Listen-jump need — cap audio at 20 min per file, so calls over ~18 min split into overlapping chunks (ffmpeg) and stitch. Stereo bills per channel. Results can take up to a day.

### 6.4 Summary — `comms_summarize_sweep` (S3)

Recurring job (`*/2`, Part B of `ref/migrations/2026-10-15_comms_s3_summaries.sql`). Code: `services/commsSummarizeSweep.js` (tick), `services/commsSummaryGround.js` (the strict validation + grounding — pure), `lib/aiPrompts/commsSummary.js` (the prompt), `lib/internal_functions/commsSummarize.js`. Lock `comms_archive_summarize:<db>` (a database name over 32 characters is hashed to keep GET_LOCK's 64-character limit; the same for the transcribe lock); at most 3 calls a tick, none started after 30 s (a call can run ~100 s and the scheduled-job runner is serial).

- **Mode** (`comms_summarize_mode`): `off` | `sample` (the transcripts of `comms_eval_items`; the short gate bypassed) | `on` (every `transcribed` call recording and voicemail, newest first). Summaries exist only where a transcript does.
- **Gates, in order:** Restrict → `skipped:restricted` (never sent; back to pending once unrestricted); a CALL with `comms_media.duration_s` (AssemblyAI's measured length) under `comms_min_summary_s` → `skipped:short` (mode `on`; voicemails exempt); empty text → `skipped:empty`; no real speech → `skipped:no_speech` (below; mode `on`, voicemails included); the shared monthly cap (§6.5) → wait. A pending staff request (S3c) bypasses the short and no-speech gates.
- **The no-speech gate (v4.2)** — `commsSummarizeSweep.speechGate(segments, fullText)`, pure and deterministic (no model call, no `ai_calls` row, nothing charged) → `{skip, reason, counts}`. Born of the QA of 1,304 v4.1 summaries: 113 stated absences and 61 narrated, mostly on calls that were only greetings, phone menus, hold messages, call screening or "Hello? Hello?". Every SENTENCE holding a recording cue is dropped — the RECORDING cue below, plus "you've reached" (not "reached out"; gate only: it drops its own sentence, never makes a live receptionist a recording) — because a cue sits mid-sentence in call screening ("…state your name after the tone and Google Voice will try to connect you") and a greeting's other sentences are cues too, while a message left before or after a menu is its own sentence. A sentence ends at `.` `?` `!` followed by a space or the segment's end — not after a title (Mr., Dr., St.…) or a single letter (an initial, "a.m."); a number before a period ends one ("…248-555-0100. Please leave…"). A speaker's SUBSTANTIVE words are what remains minus the greeting / filler / dead-air vocabulary (`commsSummaryGround.contentWords`: hello, hi, yes, okay, um, bye, thanks, "can you hear me", "are you there", "thank you for calling", "have a nice day"…); a token of 7+ digits (a phone number, one token when hyphenated, dotted or unbroken) counts 2 on its own. The call is skipped only when NO speaker has 2 substantive words (`SPEECH_MIN_WORDS`, kept at 2 by the live measurement of all 2,359 transcripts: zero false skips; 3 would drop real three-word messages): one stray word ("Maria?", a first name given to a screener) is no conversation, while any two ("Call me.", "It's Maria.") or a call-back number keep it. Conservative by design — a lost summary of a real call is worse than a needless one, so anything the vocabulary and the cues do not recognise counts as speech. Existing summaries are untouched: the gate runs only where the sweep makes a summary (new rows and redos). `comms_summaries.skip_reason` `no_speech`; the tick's `skipped_no_speech`.
- **The call:** `aiService.call` (credential 12), promptKey `comms_summary`: the transcript as `userInput` — `[mm:ss] SPEAKER: words` lines, wrapped as untrusted data, so speech saying "ignore your instructions" is just text — and trusted context in `vars`: the kind (call / voicemail), the firm-local date, the direction, the contact whose number it was ON THE CALL DATE (`contact_phones` windows; exactly one → its name, else "unknown" — never a guess) and that contact's open case numbers (≤ 5); since v3 also the call's firm-local calendar day (for resolving relative dates) and the FIRM CONTEXT — the staff names (`users`: every authorized human, IT / SU included — `user_auth` authorized, `roles` not empty and without `automation`; "First Last (user_name)" when the user name adds one; ≤ 40) and `comms_summary_firm_context` (free text an SU writes: the AI receptionist, recorded greetings, call screening, names the transcriber mishears; ≤ 2,000 characters, longer = a configuration problem) — inside one `<firm_context>` block, framed as reference facts that never change the rules, with `<` `>` escaped in EVERY trusted var (a contact name can come from intake, staff names from users) so no value can close the block or open a tag (aiService substitutes `{{vars}}` in one pass, so a value holding `{{x}}` stays literal). Staff names are NOT known names for the grounding: a party is named only if the name is said on the call. `model` / effort from `comms_summary_model` / `comms_summary_effort` (whitelisted; default Sonnet 5.5 at effort `low` — on Sonnet 5.5 omitting thinking runs adaptive thinking at effort `high`, billed as output, so effort is set explicitly), `max_tokens` 16,000, `timeout_ms` 120 s for a long transcript (60 s otherwise), `consumerRef` `comms_transcript:<id>`, `outputConfig {effort}`, `noRetryOnStop` (a refusal or a `max_tokens` cut is not retried), `logContent:false` (aiService W-AI). Immediately before the call the row is re-read: still `transcribed` and its item not restricted, else skipped — nothing leaves after a Restrict or a purge that landed while the context was being looked up.

**Strict validation:** the keys above only (others dropped); a key of the wrong type, an unknown `call_type` or no `summary` fails the attempt (3 → `failed`). Since v3 `call_type` is WHO the other party is (or what the call is about) and is never `voicemail` — a call that reached a voicemail box says so in `reached_voicemail` (a boolean; missing = false; forced true for a voicemail item). A model that still says `call_type: "voicemail"` is COERCED to `other` + `reached_voicemail: true` and counted (`coerced_call_type` in the tick's output) — a label is not an ungrounded claim, so it costs no attempt (manager ruling 2026-10-15, revising strict). `dates[].resolved_date` is DERIVED (the model's reading of `date_text` against the call day), so it is not grounded: kept only as a real calendar date within [call day − 400, + 800] days, otherwise null — the item stays, grounded by `date_text` + its quote; any surface shows it as resolved, never as said. **Prompt v3** (2026-10-15, from the QA review of 34 Haiku summaries: 50% good, 41% OK, 9% poor — every poor one a role reversal; no invented numbers): the firm context; what direction means (outgoing = the firm called the other party); diarization caveats (calls usually have two parties; labels may over-split a person or label a recording; which Quo channel is the firm is NOT fixed — measured 7 of 8 incoming on ch2, one on ch1 — so it is inferred, never stated); every deadline, hearing and amount to act on stated in the summary; nothing taken from recorded announcements, menus, hold messages or greetings. **Prompt v4** (2026-10-15, from the QA review of v3 on Haiku: 82% good, no invented amounts, dates or case numbers; Sonnet on the v3 prompt swapped the same calls, so the fault is ambiguity, not model size): a "who is who" section ahead of the output format — a name said TO someone (a greeting, thanks or goodbye; "Yes, Stuart Sandweiss." in reply to "you know who it is?") names the OTHER speaker; a speaker names themselves with "this is / it's / … here / … speaking / … calling / my name is" or by answering with their FULL name ("Hello, Stuart Sandweiss."), while a greeting with a first name alone ("Hey, Stuart.") names the other speaker even as the first line; on an outgoing call the FIRST speaker is usually the callee (a cue, not a law: a voicemail greeting, a menu or Sonoma may speak first); a worked outgoing example; a self-check that, when a firm-made speaker greets that staff member by name, flips `parties`, every commitment's `by` and the summary together. The v3 rule against taking anything from recorded material now says "recorded greetings", so a live greeting is speech. Also: staff are `firm` even on their own personal calls, which are `call_type` `personal` + the `personal` flag (home, car, shopping, travel, family, tuition, charity, synagogue); `trustee` reaches every bankruptcy trustee, Subchapter V included; `dispute` only when the people ON the call disagree or the other party complains about the firm (a lawsuit, objection or contested claim merely discussed is not one); `documents_requested` only for what someone asks to be sent or provided, never what was already given; the prose gives each action to the speaker who said it, never states what was not said, never narrates the rules or the firm, never uses speaker labels, and reports a point settled on the call by its conclusion; no free-text field (`summary`, `follow_up.why`, any `what`) repeats profanity, not even masked ("used strong language", or left out), while a `quote` stays verbatim — the vendor's masking (first letter + asterisks) included, which grounds like any word. The variables, the `<firm_context>` block and their escaping are unchanged from v3. **Prompt v4.1** (2026-10-15, from the Haiku + v4 regression: the swap fixed on 3 of 4 real calls, but 3 of 31 fresh summaries told who-called-whom wrong — the first-speaker cue leaking into the prose): the summary's FIRST sentence states who called whom exactly as `direction` says (outgoing: the firm called the other party, the staff member named when said; incoming: the other party called the firm; a voicemail: the other party left the firm a message; outgoing with `reached_voicemail`: the firm called and left a message, or reached voicemail), and the first-speaker cue says it is for roles only. **Prompt v4.2** (2026-10-16, from the QA review of 1,304 v4.1 summaries on Haiku: 45 of 186 personal live calls had no `firm` party, their prose inverting who called): staff are `firm` named or not — on an outgoing call the person who placed it, on an incoming call the person who answered for the firm — and a personal call is no exception to the who-called-whom sentence; a message left on voicemail that opens with a greeting + a FULL name ("Hi, Stuart Sandweiss, 248-555-0100, …") is the caller introducing themself, with a short outgoing example (the rule already existed for live calls; the model missed it in left messages). The version (`'4.2'`; `ai_calls.prompt_version` is `varchar(32)`, verified live) is stamped only into `ai_calls.prompt_version` (so `ai_spend`); nothing keys on it — no re-queue, no redo, no stored summary field; a summary made before it stays until a redo or a re-summarise.

**Grounding check:** both sides are normalised — NFKC, casefolded, zero-width characters removed, thousands commas dropped ("$1,200.50" = "$1200.50"), ordinal suffixes dropped ("March 3rd" = "March 3"), then split into tokens: a NUMBER keeps its inner `.` `/` `:` `-` ("3/15", "1200.50", "10:30" are one token each), everything else breaks on any non-letter / non-digit (so "W-2, and" matches "W-2 — and"; punctuation is not evidence) — and every evidence item's `quote` must occur in the transcript on WORD boundaries ("pay 50" does not ground in "pay 500", "$50" not in "$50,000", "$1,200" not in "$1,200.50", "3" not in "3/15"). Quote length: a document request needs ≥ 3 words; a date, amount or case ref may quote 1–2 words (its claim-in-quote check ties it) — but a claim that is a BARE number once normalised (digits only: no currency word, month or case-number shape) needs ≥ 2 words unless the quote itself carries a currency sign, so "50" from "I'm 50 years old" cannot ground "$50" nor "3" from "3 kids" a date, while "$50,000" stands alone; a commitment needs ≥ 3 words unless its quote is a WHOLE segment ("Yes.", "Will do.") — every occurrence is tried and the first whole-segment one taken (its `t`, its speaker), and for EVERY commitment (v3; before, only a short one) every occurrence of its quote is tried: the first that is ONE speaker's words AND whose speaker's role in `parties[]` agrees with `by` (`firm` ↔ firm; `other` ↔ client / other; a speaker with no role cannot contradict it) — and, for a short quote, a whole segment — is taken, with its `t`. So a firm "commitment" quoted from the other party's request is dropped, and a phrase both sides said ("I will email you the documents tonight", then repeated back) lands on the right speaker's turn. This proves the quote is CONSISTENT with the roles, not that the roles are right — the one role check is the **self-address check** (v4): a party whose OWN segments greet, thank, answer or bid goodbye to its assigned name ("Hey, Stuart." from the party made Stuart; "Yes, Stuart Sandweiss." after its opening line; "bye Mr. Sandweiss") has that name nulled and its transcript listed in the tick's `self_addressed` (job_results; transcript ids, no content). The validator itself only flags: the role stays as given, nothing counts in `grounding_dropped`, and the summary shape is unchanged; the sweep's guided retry (below) is what acts on the flag. The name must follow the opener in the same clause (fillers like "so much" / "there" and a title aside; a sentence break ends it), so "hi, this is Stuart" / "hello, it's Stuart" never match, and a name followed by "calling" / "here" / "speaking" / "from" is a self-introduction. It is read on the RAW words: the name must be capitalised ("Yes, will do." is no address to Will) and must not run on into a lowercase word ("Thanks, Mark it down."). The FULL name — the assigned surname next, or any capitalised word run straight on (surname unassigned or misheard) — after a greeting (hi / hey / hello / good morning…) is a self-introduction in any segment (a split pickup "Hello." → "Hello, Stuart Sandweiss."; a voicemail's "Hi, Stuart Sandweiss again"); after a reply (yes / thanks / thank you / bye / goodbye) it is an address, outside the speaker's own first segment. A last name alone counts only after a title. Two exceptions (v4.2, from the v4.1 QA, where every call still flagged after the retry had CORRECT roles): a segment that also PLAINLY addresses a different name (a capitalised word alone after an opener, a title allowed; not a pronoun, "Sir", "Ma'am" — apostrophes removed before the lookup —, a filler, a capitalised reply word such as "Absolutely" or "Great", or a self-tail; and not a near-variant of the assigned name — sharing its first 3 letters, or its first 2 and within 2 edits: "Stu", "Stewart" are Stuart; the variant rule only ever REMOVES "another name" candidates, so a collision — Mark / Maria, John / Joan — can only make the check flag again, never miss a flag) is not counted — then a reply + the full name is the speaker's own (a split pickup: "Hello." "Hello." "Hello, Maria. Yes, Stuart Sandweiss."), and two plain addresses are two people's turns merged by diarization ("Hey, Stuart. Hi, Maria.") — ambiguous either way; and "thanks" / "thank you" + the FULL name ENDING a segment (only digits — a call-back number — or punctuation after it; a middle initial is part of the name, a sentence after it — "… Stuart Sandweiss. Bye." — is not) with at least 20 words before it (`SIGNOFF_MIN_WORDS`: well above a conversational reply, well below a letter read aloud or a left message) is a sign-off, not an address. A first name alone closing a long message ("Thanks, Stuart.") still counts: it thanks the listener as often as it signs. Not fixed: someone reading aloud on-screen text that holds their own name ("Thank you, Maria Lopez, for your payment") — the transcript cannot tell reading from speaking, so the address stands (recall kept). A summary is listed only once it is written — a purge fenced at the UPDATE never is. **The guided retry (v4.1):** when the first answer self-addresses AND the call has exactly two SUBSTANTIVE speakers — a label the validated `parties[]` gives a role, with ≥ 2 words over all its segments, none of which sounds like a recording by the RECORDING cue (v4.2: canonical recorded phrasings only — after the tone / at the sound of the tone / please leave a message (not a request — "… for / to / on / with …" — nor a caller's own "if I don't answer, please leave a message") / please leave your name, (telephone) number and (any) brief message / press 1 opening its clause (not "it told me to press 1") / the person you're trying to reach is not available / you have reached the voicemail / the mailbox is full / the person you are calling / the number you have dialed or called is / Google Voice will try to connect you / no one is available to take your call / we're unable to take your call / your call is important to us / please continue to hold / all of our agents are busy …; a phrase a live receptionist says too — "please hold", "he is not available", "would you like to leave a message?", "please leave your name and number and I will have him call you", "the number you called me from", "please stay on the line while I transfer you" — is no cue, since v4.1 counted those and so suppressed the retry on live calls) — the sweep calls the model ONCE more with the same input and a FIXED system line appended (after the staff note's framing, when there is one): "A previous answer for this call gave speaker A the name that speaker A greets or answers by name. A greeting or an answer names the OTHER speaker, never the one who says it. Re-check "parties", every commitment's "by", and the summary, then give the whole answer again." The only thing from the call in it is the speaker LABEL (validated against the segments; a vendor label shape `[A-Za-z0-9]{1,8}`, else no retry) — never the name. The retry's answer, after its own validation, replaces the first; if it still self-addresses it is kept with the name nulled; it is never retried again. Any failure keeps the first answer (name nulled): a rejected output, a refusal, a timeout or 5xx; a 401 / 403 / 429 / other 4xx keeps it too and ends the tick, as on a first call (4xx and credentials alerted). Tick output `self_addressed_retried` (a retry was made) and `self_addressed_after_retry` (of those, the FINAL answer — the retry's, or the first one kept — still self-addresses): transcript ids, listed only once the summary is written. Each self-addressed label (deduped) must be one of the two substantive speakers, else no retry; a call whose `direction` is unknown gets no who-called-whom sentence. **Its cost:** a real charged call with its own `ai_calls` row (in `ai_call_ids`, `llm_cost_cents`); the first call's reservation is released (its row holds its cost), the cap is read, and the retry is written ahead under the first call's fence (still `calling`, transcribed, not restricted, same guide) with its worst-case `est_cents` and a FRESH lease that starts one second after the moment of writing — so a retry lost in flight, finding no `ai_calls` row since that lease began, is charged as `lost_in_flight` — all BEFORE it is sent. Over the cap, or the fence lost: no retry, the first answer stands. It counts in the tick's `calls`, so the loop starts no further item past `callsPerTick` — a tick makes at most `callsPerTick` + 1 calls, and an item with a retry runs two calls back to back (each up to `timeoutLongMs`, 120 s, on a long call). At Haiku prices the retry is ~1/10 of a cent per short call; it fires only on self-addressed two-speaker calls. The prompt (`comms_summary`, since v3) states the length rules and that a commitment is quoted from the one who makes it; the bare-number floor is the validator's alone. An item's own claim must sit inside its own quote: `date_text`, `amount_text` and `case_refs[].text` must occur as whole words in the item's quote ("$50,000" quoting "the" is dropped). A commitment's quote may span segments of ONE speaker only — a splice across a speaker change is dropped. An item that fails — or is malformed — is dropped and counted in `grounding_dropped`, never repaired. **`t` is never the model's:** it is the start of the segment in which the quote begins, so Listen-jump lands on the words. `parties[].speaker` must be a speaker in the segments; a `name` survives only if it is said on the call as whole words ("Tom" is not in "tomorrow") or is the known contact. A failed validation is a fixed code (`bad_call_type`, `bad_summary`, …) — `comms_summaries.last_error` and the alerts never carry model text. The `summary` prose itself cannot be quote-checked — every rendered summary carries the R8 label; speaker roles are inferred and labelled as inferred. `personal` flags are informational (Q2: no auto-hide) — the remedy for a private call is Restrict or Purge (R9).

**Outcomes:** valid → ONE conditional `UPDATE … SET state='summarized', summary…, summary_text… WHERE state='transcribed'` (the fence, §8). A refusal → `skipped:refused` + a warning (no fallback model: a summary is optional, and a fallback would be priced on the wrong model). 401 / 403 / 429 / other 4xx → the tick stops, nothing charged (4xx alerted as configuration). A `max_tokens` stop is deterministic → `failed` at once. Timeout / 5xx / unusable JSON / a schema failure → a charged attempt, backoff, `failed` after 3; a claim past 3 attempts fails the row without another call.

**Money — every path charges, never 0 for a call that may have run:** the `calling` reservation (`est_cents`) is the WORST case, the input estimate + `max_tokens` (16,000) of output at the model's price, replaced by the billed cost on completion. A timeout's logged `ai_calls` row is charged that worst case. The `calling` write is the LAST step before the call — one conditional UPDATE that also requires the transcript still `transcribed` and its item not restricted, so nothing is reserved for a call that never starts and the last look cannot be split from the write. A `calling` row reclaimed after its lease (the call did not report back) is charged as a synthetic `ai_calls` row (`status error`, `error lost_in_flight`, no content) ONLY if aiService logged no REAL row for it since its lease began (lease start = the old `next_attempt_at` − the 15-minute lease) — a crash after the call is already counted by its real row. The sweep's own synthetic rows (`lost_in_flight`, `timeout_charged`) never count as seen: a previous lost call's charge lands inside the next lease. A `calling` row with no `next_attempt_at` (an operator "retry now") has no known lease start and is always charged — the safe direction. The two sweeps read the shared cap under separate locks — an overshoot of at most one estimate each (accepted, 2026-10-15).

**Purge race:** aiService writes its `ai_calls` row AFTER the response — after a purge that landed mid-call has already cleared the row's `ai_calls`. So whenever the transcript turns out purged after a call (or the fenced UPDATE loses), the sweep clears that `consumer_ref`'s `ai_calls` text itself.

**Surfacing (S4's thread):** `summary_text` is the call bubble's text, and a voicemail's summary rides `m.voicemail` and sits under its row on the bubble; every route that hands summaries out on a thread or call card — the two conversation routes (`routes/api.phoneComms.js`) and the two entity Communications routes (`GET /api/contacts|cases/:id/communications`, `routes/api.entityComms.js`) — writes ONE batched `admin_audit_log` row per fetch that handed any out (`tool='comms_archive'`, `details {action:'view_summary', media_ids}`, never content — `commsArchiveView.summaryMediaIds`) (search hands out summary snippets and audits its hits as `search` — §7). A summary whose `comms_summaries` row says `skipped` is NOT served — not on a bubble, not as a search snippet, not to the audit (`hideSkippedSummaries` in commsArchiveView; the page re-check in commsArchiveSearch): the queue's skip decided it should not show, but the redo path and the sweep's skip leave the old `summary_text` on the row. Only `skipped` hides — a pending/calling redo keeps showing the previous summary (above), and a transcript with no queue row serves what it has.

Plumbing: `MODEL_PRICING` has `claude-sonnet-5-5` ($2 / $10 per MTok) and `claude-haiku-5-5` ($0.10 / $0.50 — for prompts ≤ 100K tokens; $0.50 / $2.50 beyond, which the flat map does not model; the longest call is ~55K). **`ai_calls` holds NO content for this consumer:** the sweep calls aiService with `logContent:false`, so `request_excerpt` and `response` are length markers (`[omitted: N chars]`) and an HTTP / envelope / network error is a fixed code — `ai_calls` stays readable on the read-only endpoint (spend monitoring: tokens, cost, status, model, `consumer_ref`) while the summary text lives only on `comms_transcripts`, which that endpoint may not read (§7, `lib/sqlGuard`). Purge still clears both fields for every attempt by `consumer_ref` — a backstop (the strict JSON retry's first attempt never reaches the caller, so `ai_call_ids` alone could not find it).

**Per-call re-summarise (S3c)** — `POST /api/comms-archive/media/:id/resummarize` `{model?, note?}` (`services/commsArchiveResummarize.js`): any staff user who may READ the call (`canReadMedia` — else the same 404; a staff JWT only) asks for its summary to be made again, or for the FIRST time (a transcribed row whose summary was skipped, failed or never made). `model` defaults to `claude-sonnet-5-5` (or `claude-haiku-5-5`), whatever `comms_summary_model` says; `note` is an optional ≤ 500-character hint about the call's context. Refused with 409 `{code}`, nothing changed: `restricted` (never sent — R5, even for an archive admin), `not_transcribed`, `empty` (no words), `busy` (a summary call in flight), `summaries_off`, `settings`, `over_cap` (this call's worst case at its model over the cap's headroom after month-to-date and queued spend); ≤ 10 per user per hour (429). One transaction: the queue row locked (`FOR UPDATE` — the sweep's write-ahead waits on it), the transcript re-checked, `summarized` → `transcribed` (the OLD summary stays readable until the new one replaces it), the queue row → `pending` (created if absent; attempts 0), and the GUIDE upserted.
- **The guide** (`comms_summary_guides`, one row per transcript — a side table because both redo modes delete `comms_summaries` rows) holds the model, the note, its author, `requested_at` / `requested_by`, a `version` bumped on every request (a request's identity: `requested_at` is seconds-precise, two requests can share a second) and the `outcome` (NULL = pending | done | failed | skipped). The table is in `lib/sqlGuard` SENSITIVE_TABLES (staff notes are content). It drives EVERY later summary of that transcript — bulk summary redos and transcript redos included — so a bulk `{summary_model: 'claude-haiku-5-5'}` run never silently replaces a Sonnet + note summary (it is not selected; named, it is still made with the guide). A new request replaces the guide; one without a note CLEARS the note. Purge deletes it (the note is content); Restrict hides it with the summary.
- **The sweep:** a pending guide is summarised FIRST (the next tick) and bypasses the short gate (someone asked); the row's model is the guide's. The note goes as UNTRUSTED input — escaped, in a `<staff_note>` block at the top of the user turn, inside aiService's `<untrusted_user_input>` wrapper, never in the system text — and, only then, one framing line is appended to the system text (`systemAppend`: a staff hint that may be wrong, never overrides the transcript or the rules, never a source for a quote, name, date or amount); without a note the prompt is byte-for-byte unchanged. Grounding reads the TRANSCRIPT segments only and the note is not a known name, so anything taken from the note is dropped. The write-ahead also requires that no NEWER request landed since the row was read (the `version` as read) — if one did, the row goes back uncharged and the next tick uses the new guide; once a row is `calling`, a request is refused `busy`, so none can land mid-call. The done-write, `_fail` and `_skip` stamp the guide's outcome (for the version read), so `summary_pending` never sticks. **The note that shaped a summary is stamped INTO it:** `comms_transcripts.summary` → `$.guide` = `{note, note_by (users.user), note_by_name ("First Last" at the time), requested_at (ISO UTC), model}`, or `null` for a summary made without a note — so the note shown beside a summary is always the one that produced it (a later request replaces the guide row, never a stored summary), and it is hidden and purged with the summary.
- **Audit:** `details.action = 'resummarize'` with `media_id`, `model` and `note_len` — never the note. The thread decoration's fields are S4's, gated like `summary_text`: `summary_model` (`comms_transcripts.summary_model`), `summary_note` / `summary_note_by` from the summary's `$.guide` stamp (`note`, `note_by_name`), and from the guide row only `summary_requested_at` and `summary_pending` (a guide with outcome NULL); `view_summary` covers a note handed out.

## 8. Restrict and purge

Both limited to SU and SS (Q7 — may widen later), reason required, audited (§7). They are API routes, `routes/api.commsArchive.js`: `POST /api/comms-archive/media/:id/{restrict|unrestrict|purge}` with `{reason}` (1–500 chars) and, for purge, `confirm` equal to the id AND `password` — the caller's own, re-checked by `commsArchiveAdmin.verifyOwnPassword` (bcrypt against `users.password_hash`, the `/admin/elevate` pattern, which SS cannot use: it is SU-only; Fred's ruling, S4). A wrong or missing password is `403` `code:'bad_password'` (never 401 — the shell's `apiSend` answers a 401 with a re-login), audited `rejected_bad_password`, nothing purged and no `attempt` row; five failures in 15 minutes lock purge for that user (429) — each attempt is RESERVED as a failure before bcrypt runs (and released on a right password or a missing hash), so a parallel burst gets at most five guesses per instance; an account with no hash gets `403 no_password`. The UI (S4) is the ⋯ button on each archived item in Comms → Phone, drawn for archive admins (the conversation response's `archive_admin`). **Who (R9, Fred 2026-10-14):** a staff JWT (never an API key) whose user is SU (from `users.user_auth`, not the token) or listed in `app_settings comms_archive_admins` (CSV of `users.user` ids, SU console only, seeded `1` = SS, read uncached, digits only; missing / empty / garbage = SU only) and still `users.user_auth = 'authorized'` (checked per request) — one function, `services/commsArchiveAdmin.isArchiveAdmin`, which the roles arc later swaps for a `users.roles` capability. Every attempt that reaches the router, rejects included, writes an `admin_audit_log` row (`tool='comms_archive'`, `details {action, media_id, reason}`, outcome in `status`); a request without a valid credential is 401'd earlier by `jwtOrApiKey` (logged in `jwt_api_audit_log`). A purge writes an `attempt` row BEFORE the destructive step and its outcome after — if the attempt row cannot be written the purge is refused (503) — and is limited to 20 per user per hour (429, audited).

**The do-not-transcribe list** (`comms_no_transcribe`, R9 / P6) has the same WHO and audit: `GET /api/comms-archive/no-transcribe` → `{entries:[{id, phone, note, created_by, created_by_name, created_at}]}` newest first; `POST` `{phone, note?, requested_by?}` → `{entry}` — the phone loses every non-digit and a leading US `1` from 11 digits, anything but 10 digits is a 400; already listed → 409 (the UNIQUE key decides, so racing adds cannot both land); `note` trimmed, ≤ 255, optional; `requested_by` (stored in `created_by`) = who ASKED — an active staff user (`taskService.findAssignableStaff`: authorized, not the automation user), default the caller — while the audit row names who added it; `DELETE …/:id` → `{entry}`, unknown id 404. Service: `services/commsNoTranscribe.js`. It is read only at submit (§6.3): an add skips every not-yet-submitted call on the number and touches nothing stored (the summarise sweep and Re-summarise do not read it; redo skips listed numbers, §8 Redo); a remove lets future calls through, while rows already `skipped:no_transcribe` stay skipped (only `restricted` skips are revisited). `GET /api/comms-archive/admin` → `{archive_admin}` tells a page whether its CALLER passes `isArchiveAdmin` (staff JWT; any other credential → `false`, not a 403); it is not audited — it reveals only the caller's own flag and is read on every Comms open — and it gates nothing: the routes above are the gate.

- **Restrict / unrestrict** — flips `comms_media.restricted` (and hides the derived text with it). Reversible. For "this one is private" without destroying anything.
- **Purge** — irreversible, removes content everywhere we hold it. It runs under the row's sweep lock (`comms_archive_sweep:<db>` for RC call recordings, `comms_archive_media:<db>` otherwise; held → 409, retry), so no tick can be mid-row — downloading or uploading — while it runs. Ordered, idempotent steps (`PURGE_PARTS` in `services/commsArchiveAdmin.js`; S2 and S3 append theirs), then the tombstone; a failed step → 502 and NO tombstone, so the registry never claims a purge that did not happen. A pending row's purge also deletes any object already under its prefix (an upload whose row was never flipped) and stops the row from ever being fetched. What each copy gets:

| Copy | Purge does |
|---|---|
| Bucket: audio / MMS file + `stt_raw` | Delete → soft-deleted 30 days, then gone. Purging an object younger than 365 days incurs the Archive early-delete charge (cents — expected, not an anomaly). For immediate destruction an admin sets soft delete to 0, deletes, restores it (the policy at deletion time applies) — documented runbook, not an app feature |
| `comms_transcripts` (and its `comms_redo` marker, deleted) | `segments`, `full_text`, `summary`, `summary_text` set NULL; `state='purged'`; `stt_cost_cents` and the `comms_stt_jobs` ledger stay (cost and vendor ids are not content). This is PURGE_PARTS' FIRST step (`transcripts`) because it is the FENCE: the transcription sweep holds its own lock, not the archive lane's, so instead of locking, every sweep write is conditional on the row still being `transcribing` with the job it polled — a write that loses deletes the object it just stored (a failed delete there is an anomaly alert), and an `stt_raw` child inserted before the fence is removed by the next step (`derived_children`). The step also deletes EVERY object under the item's `phone/stt/…/<id>.` prefix by LISTING it (a crash between a put and its child row leaves an object no row names), and the vendor copies of the item's ledger jobs, best-effort: reported in `parts.transcripts` (`deleted` objects; `vendor` `deleted` / `owed` / `none`); an owed delete is retried by the sweep; a job whose POST timed out and was never found in the vendor list cannot be deleted by id — the vendor's 30-day TTL removes it. On a database the S2 migration has not reached, the step is a no-op |
| `comms_media` | `state='purged'`, `purged_at/by/reason`; `object_name` kept so the tombstone says what was removed |
| `ai_calls` (every row of `consumer_ref` `comms_transcript:<id>` — every attempt; the ids are also in `ai_call_ids`) | `request_excerpt`, `response` set NULL by the `transcripts` step; tokens and `cost_cents` stay (not content). A call in flight during the purge logs AFTER it — the summarize sweep clears that row itself when its fence loses |
| STT vendor | Nothing left: AssemblyAI's copy (and the sample-mode variant's) is deleted right after fetch, a job in flight is deleted by the purge itself (above), and the account's data TTL (30 days, set 2026-10-14; may drop to 7 later) removes anything a failed delete leaves; Google returns results on the job's operation with no separate transcript store (confirm retention of the operation result in S0) |
| Anthropic API | Standard API retention is ~30 days (ZDR is gated opt-in; the newest models are excluded from it) — a purge is complete at Anthropic ~30 days after the last summary attempt. Not trained on without opt-in |
| Cloud SQL backups | Not editable; the content ages out with backup retention (F5: the current setting stands). The instance keeps 7 automated daily backups and 7 days of binary log for point-in-time recovery (`ref/INFRA_GCP.md` §2, the Cloud SQL row; no on-demand backups exist, checked 2026-10-28), so purged content is gone from every automated backup and PITR copy about 7 days after the purge: the last backup taken before it rotates out 6–7 days later, when the 7th newer daily backup lands, and the 7-day recovery window passes the purge at 7 days. The `log` row and the `phone_event_log` row stay: that a call happened is the firm's record. Removing those too is a separate, explicit decision outside this design.

### Redo (S2c-2)

`POST /api/comms-archive/redo` `{mode, select, limit?, apply?}` (`services/commsArchiveRedo.js`) sends stored transcripts — or only their summaries — back to be made again with TODAY's settings (the speaker cap, the stereo variant, the summary model). Born of over-split diarization (2026-10-15: 27% of RC mono calls came back with 3–24 "speakers"; a Quo stereo call diarized as 6 garbled its summary). `superuserOnlyFor('comms_archive_redo')` — SU + step-up, a staff JWT only (never an API key) — and applies ≤ 30 per user per hour. A DRY RUN unless `apply: true`: counts by kind / provider / channels / speakers, the target variants, the estimate, the cap headroom, the media ids. Every call is audited (`admin_audit_log`, `tool='comms_archive'`, `details.action` `redo_transcript` / `redo_summary`: the selector, the outcome, counts and media ids — never content).

- **Selectors** (exactly one): `{quo_stereo_diarized: true}` (Quo, ≥ 2 channels, made with diarize), `{mono_min_speakers: N}` (1 channel, ≥ N speakers, not already made with a speaker cap — `stt_model` without `+max`), `{capped: true}` (every diarize row made under the S2c-1 speaker cap — `stt_model` `…+diarize+max<N>`; Fred dropped the cap 2026-10-15, `comms_stt_max_speakers` = 0: QA found most 3+ splits were real voices — IVR, hold, screening, extra people — and a cap merges hearings and 341 meetings dialled into from firm lines), `{summary_model: '<model>'}` (summary mode), `{media_ids: [...]}` (either mode, ≤ 200). `limit` (default 50, ≤ 200) bounds one apply; call again until `remaining` is 0.
- **Never selected:** restricted or non-archived items; transcripts not `transcribed` / `summarized` (summary mode: `summarized`); numbers on `comms_no_transcribe`; `comms_eval_items` (lane D's evaluation set refers to those transcripts) unless named in `media_ids`; a row whose summary call is IN FLIGHT (`comms_summaries.state = 'calling'`) — reported as `busy`: the summary's done-write is fenced on `transcribed`, so a flip mid-call would take its purge branch and mark the summary skipped / `purged`, never remade. The apply re-checks state / archived / restricted / not-calling in the SAME conditional UPDATE, so a row that changed since the selection is left alone (`changed_since_selection`).
- **Refused applies** (409, nothing changed): the batch estimate — STT at today's variant on the vendor-measured `duration_s`, plus each summary at its WORST case (what the summarize sweep reserves) — over the headroom: the shared monthly cap minus month-to-date minus what the sweeps have still to spend — marker rows' STT while `pending`, and every summary to come while the summarize sweep would make it (marker rows `pending` / `transcribing`, and every `transcribed` row with no queue row or a `pending` one: summary-redone rows, redone rows already stored, the ordinary backlog; never restricted rows or calls under the summary minimum) — so back-to-back applies cannot overrun it (`over_cap`); the sweep that must do the work not `on` (`sample` only when every row is an evaluation item — `mode`); a transcript redo of SUMMARISED rows while the summarize sweep would not remake their summaries (`off`, or `sample` for non-evaluation rows — `summaries_off`); either sweep's settings wrong (no summary estimate without a model — `settings`).
- **Transcript mode**, one transaction per row: `pending`, the summary fields and job refs NULL, the `comms_redo` marker written (with `prev_model`), the `comms_summaries` row deleted (the summarize sweep rediscovers it once the row is `transcribed` again). The OLD TEXT STAYS in the row (segments, full text, speakers, language): every reader — the viewer, the transcript route, search, the evaluation pages, the summarize sweep — reads only `transcribed` / `summarized`, so it is hidden while the redo runs (still in the FULLTEXT index; search's state filter drops it), and the new text replaces it in `_complete`'s one UPDATE — never half-replaced. Purge clears it in any state. The transcribe sweep submits marked rows FIRST (ahead of new calls). Only when the NEW transcript is fetched and parsed, immediately before it is stored, does it RETIRE the item's AssemblyAI JSON — both variants' parts, `assemblyai` and `assemblyai-mc`: the object (by its row and by its expected name, so a crash-orphan cannot block the store), then the `stt_raw` row — because parts are named by variant and `_storeRaw` never overwrites. A storage failure there throws into the poll's handler (refund, alert, stop; the job is re-polled — its vendor copy is deleted only after the store). A phone provider's own voicemail transcript (other parts) is never touched; a named evaluation item loses BOTH variants' JSON, lane D's alternate included. The old vendor job was deleted long ago; the new one is deleted after fetch as usual.
- **A redo that fails or stalls never loses the old transcript.** A tick step, every mode, run FIRST (right after the lock, before the config / auth / vendor checks — pure DB work, so a broken tick never keeps a failed redo hidden) and again at the end for that tick's own (`_restoreFailedRedos`): a marker row that ended `failed` (its new main jobs failed, or transport ran out) or `skipped` at submit (restricted, no-transcribe, now under the minimum, over the per-call cap) with its text still there goes back to `transcribed` with `prev_model`, `last_error` saying why, the marker deleted, and a warning (`comms_transcribe_redo_failed`, once a day, media ids only). Its summary is made again (a restricted one never — the summarize sweep's gate). A purged row is never restored (`purged`, text NULL; purge deleted the marker).
- **Summary mode**: `summarized` → `transcribed` and the `comms_summaries` row deleted. The OLD summary stays readable until the new one replaces it in one UPDATE; if the summarize sweep then skips it (settings changed, or the no-speech gate), the old text stays on the row but is no longer served (§6.4 Surfacing).

| Alarm | Severity (CLAUDE.md convention) |

| Cliff guard (§6.2) | error |

| `failed` rows (archive / transcribe / summarise) | warning first per subject, error on repeat — archive: always error, one row per day (`comms_archive_failed`); `failed` means the call passed 90 days (RC recordings) or 30 days of failing / waiting passed (MMS, Quo recordings) — §5 |
| Quo recording still "not yet" 24 h after the call | warning, error on repeat (`comms_archive_quo_not_yet`) |
| Delete detection could not finish its night's slice | warning, error on repeat (`comms_archive_verify_incomplete`) |
| Archive row still failing after 8 provider-side attempts | error, one row per day (`comms_archive_stuck`) — the row keeps retrying every 6 h |
| Credential refresh failure (stops the RC side) | `oauthService` already pages `critical` (`oauth:<id>`) on the second consecutive refresh failure, and the error sweep reopens it while `oauth_status='refresh_failed'`. The sweeper adds `comms_archive_no_auth:<cred>` for any no-Authorization state (disconnected, refresh failed, URL outside `allowed_urls`) and RC 401/403: warning, error on repeat within 24 h |
| Archive storage unavailable (bucket unset, a required permission missing, upload refused or timed out) | warning, error on repeat within 24 h (`comms_archive_storage`); the tick ends, no row is charged |
| A phone adapter that cannot archive (not in `phoneService`'s registry, no `capabilities.archiveFetch`, or a function the sweep calls absent) | error from the first tick — a code / deploy defect, not a blip — one row per provider per sweep per day (`comms_archive_adapter:<provider>`); that provider stops for the tick, no row is claimed, the media sweep's other provider goes on |
| Call on a line that is not a `phone_lines` row | warning, error on repeat, one group per line (`comms_archive_no_line:<line>`); past 90 days the row turns `failed` (error) and stops retrying |
| Call-log answered with records, none for the requested session | error, one row per day (`comms_archive_session_mismatch`) |
| A provider response that does not match its documented shape (Quo) | error, one row per day (`comms_archive_shape_drift`); the rows wait uncharged |
| Quo 403 on a line (resource-level: Quo forbids per line) | warning, error on repeat, one group per line (`comms_archive_quo_forbidden:<line>`) — the rows wait 24 h, uncharged; a tick of nothing but 403s across ≥ 2 lines also raises the credential no_auth alert |
| A Quo call status outside {completed, no-answer} | error, one row per day (`comms_archive_quo_status_drift`), naming the value |
| RC voicemail listing off its probed shape (non-200 other than 429, records / paging missing, > 3 pages, a bad record, a thrown listing) | error, one row per day (`comms_archive_rc_vm_listing_drift`) — its own group |
| No COMPLETED RC voicemail listing in 6 h | warning, error on repeat (`comms_archive_rc_vm_listing_stale`). The backstop for every quiet miss: a 429 on the listing is deliberately silent per tick, and skipped hours raise nothing themselves |
| No Quo voicemail archived yet, though calls have been checked | warning once a day with checked / held-404 / none / found counts, ERROR once it has persisted 48 h — it emails only from then (warnings ride the digest of something else) — until the first one is archived (`comms_archive_quo_vm_sanity`) |
| Archived object missing outside a purge (delete detection) | error, one row per day (`comms_archive_missing`) |
| Delete detected outside a purge | error |
| AI monthly cap reached (transcription + summaries) | warning the first day, error once it has held 24 h (`comms_transcribe_cap`, one per day) — new transcriptions and summaries wait, nothing is charged |
| Summaries: a setting is wrong (mode, model, effort, minimum), or Claude refused us (401 / 403 / other 4xx) | error when it stops summaries, else warning; one per day (`comms_summarize_config`) |
| Summaries: Claude declined a call (refusal) | warning, one per day (`comms_summarize_refused`) — the transcript is untouched |
| Summaries: rows now `failed` | warning, error on repeat (`comms_summarize_failed`) |
| Transcription backlog older than 48 h | warning, one per day (`comms_transcribe_backlog`) |
| Transcription: STT credential refused (no Authorization pre-flight, a 401/403) | warning, error on repeat within 24 h (`comms_transcribe_no_auth:<cred>`) — with the endpoint, status and vendor text; the tick stops, nothing charged |
| Transcription: storage / signing unavailable (header read, the signing proof, signing; AssemblyAI unable to download our URLs while none complete) | warning, error on repeat (`comms_transcribe_storage`) — no client audio is sent until the proof passes |
| Transcription: a setting is wrong (mode, credential id, gate knobs, keyterms) | error when it stops transcription, else warning; one per day (`comms_transcribe_config`) |
| Transcription: a vendor response or audio header off its expected shape | error, one per day (`comms_transcribe_drift`) — parked uncharged, never "done" |
| Transcription: rows now `failed` | warning, error on repeat (`comms_transcribe_failed`) |
| Transcription: the header estimate disagrees with the vendor's `audio_duration` (> 20% and > 3 s) | warning, one per day (`comms_transcribe_duration_drift`) — the short / cap gates may be misjudging |
| Transcription: a stored object or `stt_raw` row disagrees with what a crashed tick left; an object left behind by a purge race; a vendor job id unsafe to put in a URL | error, per row (`comms_transcribe_anomaly`) — parked 6 h, never overwritten |
| Transcription: a POST got no usable answer (the vendor MAY hold a job), or such a job was never found in the vendor's list in 24 h | warning, one per day (`comms_transcribe_orphan`) — the 30-day TTL backstops |
| Transcription: a vendor copy still not deleted after 5 tries | warning, error on repeat (`comms_transcribe_delete_owed`) — retried with backoff |
| Transcription: AssemblyAI refuses the request itself (a 4xx other than 401/403/429) | error, one per day (`comms_transcribe_config`) — tick stopped, nothing charged |
| Transcription: the last 3 POSTs all came back unreadable or without an answer | error, one per day (`comms_transcribe_breaker`) — submissions pause 6 h from the newest; polling, the orphan search and deletes go on |

Every archive alert carries a per-UTC-day `dedup_key` (with the severity in it where a warning may escalate): `lib/alerting` turns a repeated `dedup_key` into a silent no-op — no row, no `alert_state` bump — and the hourly digest emails rows grouped by `group_key` with a 6 h per-group cooldown. So a backlog of `gone` rows pages once, never once per row.

**Delete detection (F3):** `comms_archive_verify` (`services/commsArchiveVerify.js`), nightly at 07:15 UTC, stats the `archived` rows whose `id % 7` equals the UTC day number `% 7`, paging through the whole slice until done or its deadline. Every object is checked every 7 days; one missed night still checks it within 14 days and two within 21 — inside the 30-day soft-delete window, so an unexplained delete is caught while still restorable (a soft-deleted object is not a live object, so it counts as missing). A night that cannot finish its slice alerts (`comms_archive_verify_incomplete`, warning then error). Missing → a guarded stamp `last_error 'verify: missing <date>'` on rows still `archived` (a purge landing between the stat and the stamp is never reported) — the state stays `archived` — and one error alert per day (`comms_archive_missing`); a GCS failure ends the run with a storage alert and never reports anything missing; lane A's `_s0/` probe prefix is excluded. It runs whether or not `comms_archive_enabled` is on, like the cliff guard: read-only, and a delete during a pause is exactly what it exists to catch. Recorded in `ref/INFRA_GCP.md` (lane A). (The alternative, a Pub/Sub `OBJECT_DELETE` push, was declined as the more moving parts; if ever adopted, the push subscription authenticates with an OIDC token the endpoint verifies — never an open endpoint.)

**Health (S4):** `GET /api/comms-archive/health` (`superuserOnlyFor('comms_archive_health')`: SU + step-up) — counts by kind × provider × state (+ restricted), oldest pending per kind / provider and the commonest pending `last_error`s, each sweep job's schedule and last `job_results` row, the open `comms_archive*` alerts, and (once S2's tables exist; null until then) transcript states, skips by reason, the oldest waiting transcript, and month-to-date STT spend from the `comms_stt_jobs` ledger (`monthToDateCents`; summaries' cost joins with S3). Shown as a collapsed **Comms archive** section in the System Alerts pane (`public/systemAlerts.html`), read only when opened (F4: an Admin pane panel; its own Admin tile is a `ref/plans.md` item — the launcher surface was mid-edit by the access-control arc).
